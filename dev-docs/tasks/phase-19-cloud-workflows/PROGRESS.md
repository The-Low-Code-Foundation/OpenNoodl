## Log

- **2026-07-26** — **WF-002 complete.** Eight new step kinds on WF-001's `StepExecutor` seam; the engine's ordering/error-routing/cancel/timeout/concurrency semantics are untouched (the WF-001 suite passes unchanged, which is the evidence). The structural call: CF11-001/002/003 all specify *browser* nodes — signal ports, `triggerOutput`, `triggerOutputAndWait`, per-instance state — and WF-001-SEMANTICS overrides that by name ("WF-002's Series-1 workflow nodes plug into the same `StepExecutor` seam as additional step kinds"). The two models are genuinely incompatible, not stylistically different: there are no signals to trigger, nothing can trigger-and-await because the engine owns scheduling, and there is no per-instance state because runs are in-memory. Full translation table in `WF-002-NOTES.md` §2. Port names follow the **real** client nodes over the CF11 sketches where they differ (`ontrue`/`onfalse`/`result`/`isfalse` from the shipped `Condition` node, not the sketch's camelCase). Four WF-001 overrides, all recorded: **Try/Catch is not a kind** — `onError` edges already are it and a step has no body to guard, so a Try/Catch node would be a second way to say one thing that could not actually wrap anything (mapping table in `steps/errors.ts` and the docs, so someone looking for it finds the answer rather than assuming it was forgotten); **conditions are declarative, not eval'd** — a workflow definition is persisted, deployable, MCP-authored JSON, so an `eval`'d expression string in one is an RCE surface behind an admin credential, and PLAT-003/LEARN-001 both spent effort removing `eval` from this tree (cost stated honestly: arithmetic inside a condition is not expressible, compute it in a function); **`for-each` iterates a function, not a sub-graph** — the per-item unit stays a real catalogued node graph, which keeps "a workflow node is a node" true, and a nested scheduler is deferred; **`merge` does not wait** — topological order already guarantees every predecessor finished, so CF11-001's arrival-tracking machinery is unnecessary, and its useful half survives as `mode:"all"` failing loudly on a missing source. Four additive engine changes, of which one was genuinely required by CF11-002: a failed step's outcome now carries `{error}` so an `onError` handler receives `previous.error` — before this a catch branch could see *that* something failed but not *what*, which made CF11-002 unimplementable (the brief's "fix it in the runtime rather than working around it in nodes"). The others: `routes` (named conditional edges, validated and folded into the acyclicity check), `stepResult(output,{select,halt})` (branded with `Symbol.for`, not a `__field`, because step output is arbitrary user JSON and any string key could collide), and `ctx.upstream`. **Catalog — the one reinterpreted success criterion.** Step kinds structurally *cannot* enter `node-catalog.json`: it is generated by running the two node registers, `catalog:check` fails on drift, and a hand-written entry would be deleted by the next generation (same structural reason library module nodes are documented as out of catalog scope). This is explicitly *not* the WF-005 exemption — WF-005 correctly shipped with no catalog *and no equivalent* because a trigger adds no vocabulary, whereas WF-002 adds nine things an author must know. So what the requirement buys was delivered in the form the artifact has: a versioned spec table shaped like a SUB-005 enrichment entry, served at `GET /admin/workflow-step-kinds` **by the running backend** (so it cannot drift from what that backend executes), an MCP `list_backend_step_kinds` tool described to be called *before* authoring, the same table driving write-time validation (unknown kind / missing param / malformed condition / bad route name → 400 naming the problem, and refuse-to-start on load), and a coverage-gate test that is the local `catalog:merge:check --require-coverage` — it fails if the spec table, the `StepKind` union and the executor table diverge, or if a kind is undocumented. Not covered, and said so: SUB-006's validator does not see workflow definitions at all (it validates project graphs against the node catalog) — an unowned follow-up if workflows ever get a canvas. **Debounce deferred**, argued not omitted: it is inherently about repeated invocations within one persistent node instance, which WF-001 has no concept of, and faking it would mean inventing cross-run state the durability policy explicitly lacks — it would be silently wrong after any restart. The problems it solves already have honest answers (the `concurrency` cap serialises overlapping runs; rate limiting belongs at the WF-005 trigger where the noise arrives). Wait/delay carries the cost warning CF11-003's brief demanded be explicit rather than assumed — no frames, holds a `concurrency` slot, does not survive a restart, billed occupancy — plus a 24h cap enforced at *write* time so the rejection lands on the author, not in production at 3am; a test asserts the warning is still in the docs. Verified: 327/327 package specs (37 files, 68 new), including an end-to-end suite over a real `BackendService` with **real CloudRunner cloud functions** — `for-each`'s three real invocations are proven by three distinct echoed Response bodies rather than a spy count, `retry` re-invokes a genuinely 400-ing function and routes the exhaustion to a handler that receives `previous.error.statusCode`, and a run parked in a 5-minute wait cancels promptly over the real cancel route. Build green, `catalog:check` + `catalog:merge:check` green, `noodl-mcp` 50/50. Residuals: **no live-editor pass** (a worktree cannot run the editor — `lerna exec` resolves to the main checkout) and there is no editor authoring UI for WF-001 workflows anyway, so "appears in the node picker" has no referent; History Panel/overlay render not re-smoke-tested (records asserted end to end, so the data is provably right — this was already WF-001's own residual); the new `nodeType` vocabulary (`branch`, `for-each:perItem`, …) is untested against the overlay's renderer; `for-each` concurrency above 1 works but is unmeasured under load.
