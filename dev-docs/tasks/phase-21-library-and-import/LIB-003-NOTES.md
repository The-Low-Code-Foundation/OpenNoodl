## 2. Placeholder icons replaced

The three new modules shipped clearly-labelled procedural placeholders. Replaced
with icons authored to the **measured** house style rather than to a guess: the
existing set is 680×384, **opaque white** background, a single centred glyph in a
~174 px square with even margins (sampled from `font-awesome-solid`, `qr-scanner`
and `chart-js`; the badge navy is `#1D3050`).

| Module | New icon |
|---|---|
| `lucide-icons` | The `font-awesome-solid` treatment exactly — same navy rounded-square badge, same 174 px box at the same offset — with a white **stroked** Lucide glyph. The stroke-vs-fill contrast is the honest visual difference between the two icon sets, and it makes the three iconsets read as one family. |
| `qr-code` | A **genuine** QR code, generated by the module's *own vendored* `qrcode-generator` (run in a sandbox), encoding `https://nodegx.dev` — 25×25 modules at 7 px. Flat black to sit beside `qr-scanner`. The white canvas supplies the quiet zone, so it is a real scannable code, not a drawing of one. |
| `confetti` | A centred burst cluster with a solid core, deterministic (seeded) layout. The placeholder bled off all four edges, which no other icon in the set does. |

Generated as SVG → `rsvg-convert` → RGBA PNG (matching the set's existing colour
type). Sources are not committed — they are a one-shot generator, and the SVG
would be a second source of truth for a raster asset.

## 3. Deploy-build check of the scanner refactor

**What was already covered:** `tests/utils/projectmodules.test.ts` pins the
scanner against a *synthetic* fixture and a *synthetic* 5-line template.

**The gap:** the deploy path is
`HtmlProcessor.process` → `injectIntoHtml(projectDir, static/deploy/index.html, baseUrl, cb)`
(`packages/noodl-editor/src/editor/src/utils/compilation/build/processors/html-processor.ts:96`).
Neither the real deploy template, the real library modules, nor the
absolute/sub-path `baseUrl` prefixes a real deploy uses were exercised anywhere.

**What was run.** The scanner was bundled standalone with esbuild (it depends only
on `fs`/`http`/`https`/`vm`/`ajv`, so it needs no Electron) and driven against the
**real** `packages/noodl-viewer-react/static/deploy/index.html` for **all 29
library module projects × 3 prefixes** (`/`, `/app/`,
`https://cdn.example.com/app/`). Every emitted `<script src>`/`<link href>` was
resolved back against the project directory the deploy copy step ships.

> 29 module projects × 3 prefixes · **75** asset refs resolved · **0** scanner
> warnings · **0** problems — every injected module asset exists in the deployed
> project dir, no `<%modules_*%>` token survived injection.

Spot-verified by eye, and the interesting cases are all correct:

- a project-relative iconset stylesheet under an **absolute** baseUrl →
  `https://cdn.example.com/app/noodl_modules/lucide-icons/styles.css`
- the same under a sub-path → `/app/noodl_modules/font-awesome-solid/styles.css`
- a remote sheet stays verbatim → `https://fonts.googleapis.com/css2?family=Material+Icons`
  (the `startsWith` fix, exercised on real content)

**Also re-verified headlessly:** the Electron/Jasmine-only
`projectmodules.test.ts` was replicated against the bundled scanner — **9/9 pass**,
including the **byte-identical** `expected-inject.snapshot.txt` golden. And
`packages/noodl-editor` `tests-unit/erg-002` (plain jest, no Electron):
**4 suites / 33 tests pass**.

**What this does NOT reach — the honest boundary.** This exercises the
scanner→injector contract in the deploy *shape*. It does not run the real deploy
build: no `ProjectModel`, no webpack viewer bundle, no file-copy step, no browser.
So "the injected HTML is correct" is proven; "a deployed app boots and the module's
nodes work" is **not** — that is the live pass. `npm run test:ci` for the editor
was deliberately **not** run: it spawns Electron and would have collided with the
concurrent session's single-instance lock.

## 4. Module-node catalog integration — re-confirmed, still absent

The earlier finding stands, now with numbers rather than a spot-check.

- `scripts/node-catalog/generate.js` contains **zero** references to
  `noodl_modules`, `defineModule`, or `projectmodules`. Its only `module` hit is
  an unrelated type field. **No mechanism exists** to get runtime module nodes
  into the catalog — this is a structural absence, not a bug.
- Both catalog artefacts (`node-catalog.json`, `node-catalog-enriched.json`)
  contain **153** node types, and **0** of the **25** module node types measured
  in this pass appear in either. Chart.js's node is absent, as previously
  recorded, and so is every other one.
- The consequence is visible in `library:check`: **all 48** warnings across the
  whole library are `unknown-node-type`, and every one is a module-provided node
  — 47 for `Avatar`, 1 for `module.inlineHtml`. These take SUB-004's documented
  dynamic-node **"skip port checks"** path: tolerated by the validator and the AI
  authoring stack, port-unverifiable by either.

**Not built** — out of scope by instruction, and it is a design question (the
generator would have to execute untrusted module JS) rather than a missing wire.
