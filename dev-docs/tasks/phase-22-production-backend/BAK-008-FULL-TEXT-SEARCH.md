## Objective

Per-collection opt-in full-text search backed by SQLite FTS5: pick the text fields, get a search endpoint with ranking and highlighting, a search option on the query surface, and index maintenance that cannot drift from the data.

## Background

Search is where SQLite quietly embarrasses bigger stacks: FTS5 ships in the engine — no Elasticsearch sidecar, no sync pipeline, no ops. For the product's wedges it is a direct hit: "search my notes app" is the first feature every tutorial app wants, and an agent that can flip on search for a collection via MCP is a great demo beat. The task is deliberately Tier 3 — nothing depends on it — but it is cheap because the engine already contains it.

**Verify first**: FTS5 is a compile-time SQLite option. `better-sqlite3` bundles it; Node's bundled SQLite (`node:sqlite`) must be checked on the engine WF-004 actually chose. If absent there, record it and let the finding feed the engine decision's ledger (it would be a genuine point for Option B) — do not work around it with a JS search index.

## Current State

- No search anywhere in the backend path; the query grammar (`QueryBuilder`) covers structured operators only; the Parse clients' `$text` operator is not emitted by our runtime nodes (verify — if `cloudstore.js` can emit it, supporting that shape is the natural wire surface).
- Schema manager owns table DDL — the place FTS shadow tables and their sync triggers belong.

## Desired State

- **Config**: per collection, `search: { enabled, fields: [...], tokenizer? }` in backend config — panel/dashboard editable, MCP-editable.
- **Index**: an FTS5 shadow table per enabled collection (`external content` mode against the real table to avoid duplicating storage), kept in sync by SQL triggers generated by the schema manager — sync is the database's job, not application code's, so no write path can forget it. Schema changes (add/remove indexed field) rebuild the shadow table; rebuilds are explicit, progress-reported, and safe to re-run.
- **Query surface**: search term + optional structured filter combined (FTS match joined with the normal WHERE the grammar already builds), ranked by BM25, with optional `snippet()` highlighting. Wire shape: `$text`-compatible if the client already speaks it, else a `search` parameter on the existing query POST — decide against the client code, record it.
- **Node surface**: Query Records gains a **Search** input port (string; empty = no-op) rather than a new node — stays inside the existing family (no third node family, per phase 19's constraint). Catalog entry updated; works with BAK-001's Live option (a changed record re-matches).
- **Permissions**: search results pass through BAK-003's ACL filtering exactly like queries — the FTS join must compose with the ACL SQL rewriting, with shared tests.
- Loud-failure: engine without FTS5 → enabling search fails with an explicit capability error surfaced in panel/status; never a silent LIKE fallback.

## Scope

### In Scope
- [ ] FTS5 availability verification against the chosen engine (finding recorded either way)
- [ ] Config shape + panel/dashboard + MCP surface
- [ ] Shadow tables (external content) + generated sync triggers + explicit rebuild path
- [ ] Combined search+filter+ACL queries, BM25 ranking, snippets
- [ ] Wire-shape decision (`$text` vs. `search` param) recorded and implemented
- [ ] Query Records Search port + catalog update
- [ ] Tests: sync-under-all-write-paths, rebuild idempotence, ACL composition, ranking sanity
- [ ] Docs incl. tokenizer notes (unicode61 default; no language-specific stemming promises)

### Out of Scope
- Fuzzy/typo-tolerant search, synonyms, faceting
- Cross-collection global search endpoint (per-collection only in v1; the dashboard may fake it client-side)
- Language-specific stemmers/CJK segmentation (document the unicode61 reality)
- Search over file *contents* (BAK-006 metadata fields are searchable like any others)

## Implementation Steps

1. **Verify FTS5** on the real engine; record.
2. **Schema-manager work**: shadow table + trigger generation + rebuild.
3. **Query integration**: FTS join composed with grammar + ACL rewriting; ranking; snippets.
4. **Wire + node + catalog + MCP + panel.**
5. **Tests + docs.**

## Success Criteria

- [ ] Enable search on a collection via the panel *and* via MCP; insert/update/delete through every write path (classes route, BYOB route, workflow, import) — index stays consistent (tested)
- [ ] Search "quick brown" matches, ranks sensibly, returns highlighted snippets, and respects a structured filter and ACLs in the same query
- [ ] A user who cannot read a record cannot find it via search (shared ACL tests)
- [ ] Rebuild after adding an indexed field is explicit, reported, idempotent
- [ ] On an engine without FTS5: loud capability error, no degraded fallback
- [ ] Query Records Search port works live in a running app

## Risks & Mitigations

| Risk | Mitigation |
|------|------------|
| FTS5 missing from `node:sqlite` builds | Step-1 verification feeds the engine ledger; no silent workaround |
| Index drift via an unanticipated write path | Sync lives in SQL triggers — the database enforces it; the write-path matrix test proves it |
| FTS join breaks ACL rewriting | Composition tests shared with BAK-003's suite |
| External-content pitfalls (rowid mapping) | Well-documented FTS5 pattern; rebuild path is the recovery hatch |
| Tokenizer expectations (stemming, CJK) | Documented honestly; no promises beyond unicode61 |
