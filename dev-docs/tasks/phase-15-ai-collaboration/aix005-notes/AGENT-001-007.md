## Reuse: byob-realtime's SSE client

**Not reused for the transport, and the reason is that it is not an SSE client.**

`byob-realtime.js`'s `RealtimeSSEConnection` is a *NodeGX-backend protocol* client that
happens to travel over SSE. Its whole body is protocol: it listens for `connected`,
`change` and `resync` frames, extracts a server-minted `clientId`, POSTs a subscription
set to `/realtime/subscriptions`, and maps `create`/`update`/`delete` onto the same
callback shape as the Directus WebSocket transport so `Subscribe To Changes` can be
transport-agnostic. Its interface is `(baseUrl, token, collection, filter)` →
`onEvent(event, records)`. There is no generic "deliver arbitrary SSE frames" behaviour to
extract, and it deliberately delegates reconnection to `EventSource` (see its own comment:
"EventSource reconnects automatically … no manual backoff needed"), which is the opposite
of what AGENT-001 needs.

So this is not a second tap on the same transport; it is a different consumer of the same
*browser API*. Two nodes both calling `new EventSource(...)` is the same kind of overlap as
two nodes both calling `fetch`.

What *was* shared, and what was deliberately not:

- **`nextReconnectDelay`** — `sse-connection.ts` has `backoffDelay(attempt, base, max)`.
  byob's version is the same curve with base and ceiling hard-coded at 1000/30000, and
  AGENT-001 exposes both as inputs, so it could not be called directly. Rather than edit
  `byob-realtime.js` (a shared file, and other sessions are live), the duplication is
  parameterisation and is **pinned by a test**: `agent-sse-connection.test.ts` asserts
  `backoffDelay(n, 1000, 30000) === nextReconnectDelay(n)` for n in 0..11, so the two
  cannot drift silently. If someone later wants one implementation, replace byob's body
  with a call to `backoffDelay` and that test still passes.
- **The `'EventSourceImpl' in options` injection idiom** — copied verbatim from
  byob-realtime, including the reason (an explicit `null` must beat a global).
- **`buildSSEUrl` / `RealtimeSSEConnection`** — not touched. Nothing in AGENT-001 changes
  BAK-001's behaviour.

## Deviations from the phase-3.5 specs, with reasoning

The AGENT-001 and AGENT-007 specs are from January 2026. Reviewed against the codebase as
it is now; the deviations are below. Nothing was changed for taste.

### 1. The default transport is `fetch`, not `EventSource` — the big one

The spec is built entirely on `EventSource`, then spends a "Limitations & Workarounds"
section on the three things `EventSource` cannot do: send an `Authorization` header ("send
auth token as a query parameter"), send a request body ("create session/channel via POST
first"), and… that is exactly the shape of every agent backend. An AI chat endpoint is a
POST with a bearer token that answers `text/event-stream`. The spec's workarounds mean
putting a token in a URL and inventing a two-step session protocol on the server.

`fetch` with a streamed body is universally available in 2026 and removes all three, plus
two more that matter for this node specifically:

- **Named events without pre-declaration.** `EventSource` delivers `event: token` only to
  a listener registered in advance, which is why the spec needs an `eventType` input. When
  we parse the wire format ourselves, every event type arrives.
- **Clean EOF is distinguishable from a drop.** This is the one that decides correctness
  (see deviation 3).
- Plus: an explicit `Last-Event-ID` on resume, which works for POST streams too, and
  reconnection under our own control rather than the browser's.

So `transport` is an enum, `auto` prefers fetch wherever fetch exists, and `eventsource`
remains fully implemented and tested for authors who specifically want the browser's own
reconnection. Both transports feed one state machine, so the outputs are identical either
way.

**Honest downside:** `EventSource` is battle-tested and our reconnection is not — it is
only unit-tested. The fetch path also loses the browser's automatic `Last-Event-ID`
handling, which is re-implemented here explicitly.

### 2. Errors and state are outputs, following the AIX-005 lifecycle convention

Renames from the spec, to match the convention shared with the WebSocket node (AGENT-002)
so an author can swap one for the other:

| Spec | Here |
|---|---|
| `isConnected` (boolean) | `connected` (boolean) |
| — | `connectionState` (string enum) |
| `error` (string) | `lastError` (string) |
| — | `retryCount` (number) |
| `connected` (signal) | `onOpen` |
| `disconnected` (signal) | `onClose` |
| `messageReceived` (signal) | `onMessage` |
| — | `onError` |

`connectionState` is new and is the point of the exercise: the spec's model has no way to
express "reconnecting", so a failing reconnection is indistinguishable from a slow server.

`message` (the spec's raw event object output) was **dropped** in favour of the flat
`raw` / `eventType` / `lastEventId` ports, which carry the same information and are
directly wirable. If someone wants the object back it is three lines.

### 3. `reconnectOnStreamEnd` defaults to **false**, against the SSE protocol's own default

The SSE protocol says a client should reconnect when the server closes the stream. For an
agent response that is actively harmful: the response finishes, the client reconnects, the
request is re-issued, and the model generates the whole answer again — forever. So a clean
end goes to `closed` and fires `onClose`, and resuming is opt-in.

**Caveat, stated plainly:** this is only implementable on the fetch transport.
`EventSource` cannot tell a clean EOF from a drop (the HTML spec says reconnect in both
cases), so under `transport: 'eventsource'` a server that closes the stream looks like a
reconnect loop. Documented on the input's tooltip and in the enrichment entry. It is
another reason `auto` prefers fetch.

### 4. Delivery semantics are a named, observable output

The spec does not mention them. The umbrella task explicitly asks. The rule implemented:

- No `id:` fields on the stream → a reconnect cannot resume → events during the gap are
  lost → **at-most-once**.
- `id:` fields present → the resume point is sent on reconnect → the server may replay →
  **at-least-once**.
- `id:` present and `dedupeById` on (default) → replays inside a bounded window of
  recently-seen ids are dropped → **at-least-once-deduped**, i.e. the graph sees each id
  once.

`deliverySemantics` is an output computed from what the server actually sent, not from
configuration, and `duplicatesSuppressed` counts what was dropped. The dedupe window is a
bounded `RecentIds` (512 by default) rather than an unbounded Set, because an unbounded set
in a long-lived agent UI is a leak by construction.

The spec listed "Last Event ID — resume from last message on reconnect" under *Future
Enhancements*; it is here, because without it "no duplicated messages after a reconnect"
has no meaning.

### 5. Retry policy is exponential backoff with a classified terminal case

Spec: a fixed `reconnectDelay`, retried forever, on any error. Here: backoff from
`reconnectDelay` doubling to `maxReconnectDelay`, with `maxRetries` (0 = unlimited), and a
distinction the spec does not make:

- **`error` is terminal** — nothing further will happen. 4xx (except 408 and 429), a
  malformed URL, an environment with no usable API, or a spent retry budget.
- **`reconnecting` means another attempt is coming.** 5xx, 408, 429, a dropped socket.

A server's `retry:` field, when it sends one, overrides the configured base delay — it is a
direct instruction.

### 6. AGENT-007 nodes: kept all four, changed three implementations

All four spec'd nodes exist with the spec's type names and signal names.

- **`parseJSONArray`** — the spec's approach is `JSON.parse(buffer)`, and on failure
  `JSON.parse(buffer + ']')`. That reports success on truncated data and fails outright
  when a chunk boundary lands inside a string. Replaced with `scanJsonValues`, a real
  incremental scanner that tracks string state and escapes and counts depth. It is barely
  longer and correct at every boundary — `agent-stream-parsers.test.ts` cuts a document at
  *every* index and reassembles it. The `array` format is accordingly renamed **`stream`**,
  because the scanner handles NDJSON, concatenated objects and a streamed array with one
  code path.
- **`bufferSize` via `new Blob([...]).size`** — `Blob` is a browser global; the runtime is
  framework-neutral and also runs under SSR in Node. Replaced with a computed
  `utf8ByteLength`, and the node exposes `characterCount` and `byteCount` separately since
  the spec conflated them.
- **Unbounded growth** — the spec's accumulator concatenates into `messages` forever and
  its parser buffers forever. Both are now capped (`maxMessages`, `maxLength`) with the
  loss reported on `droppedCharacters` / `droppedMessages` / `droppedItems` and an
  `overflowed` signal, rather than dropped quietly.
- **`PatternExtractor`** — the spec's `notFound` covers both "no match" and "your regex
  does not compile". Split: `notFound` (normal) vs `failure` + `error` (a bug to fix).
  Added `firstGroup` and `namedGroups`.
- **`StreamBuffer`** — the spec has no cleanup for its interval timer. Here the timer is
  armed only while items wait, re-armed on an interval change, cleared on manual flush, and
  cleared in `_onNodeDeleted`; `flushedData` is a detached array so a later `add` cannot
  mutate what a Repeater is rendering.

### 7. Placement, language, and SSR metadata

- `src/nodes/std-library/agent/` in **TypeScript**, not `data/*.js` as the spec says — per
  the AIX-005 brief and PLAT-003. (`src/nodes/` is otherwise still all `.js`; these are the
  first typed node definitions in that tree. Both viewers already resolve `.ts`, and
  `noodl-runtime.js` already requires `./src/node` which is TypeScript, so the path is
  proven.)
- The spec's node type names are kept verbatim (`net.noodl.SSE` etc.) — `net.noodl.*` is
  genuine house convention here.
- `ssr` metadata, which did not exist when the spec was written: SSE is
  `client-only` (RUN-002 makes the instance inert server-side); Stream Buffer is `partial`
  (its interval never fires on the server, everything else works); the other three are
  safe.
- `PatternExtractor` is categorised `Data`, not `String Manipulation`, so the family stays
  together in the picker.

### 8. Not done from the spec

- **`withCredentials` is implemented but untested against a real cross-origin server.**
- **`docs/nodes/data/sse.md` and `docs/nodes/data/stream-utilities.md`** — the spec asks
  for user-facing docs pages. Not written; the catalog enrichment entries carry the same
  material in the form the editor and AIX-002 actually consume. Filing this as an open item
  rather than claiming it.
- **The spec's `customHeaders` input** is just `headers`, and it works, so the spec's
  "EventSource doesn't support headers, document limitation" is moot on the default
  transport.

## The lifecycle matrix, and how each case is tested

Every dependency is injected, so each case is driven deterministically with no server, no
DOM and no real timers. Timers are a `Map` a test can inspect, so "no leaked timers" is an
assertion rather than a hope.

| Case | Where | How |
|---|---|---|
| Navigate away mid-stream | `agent-sse-connection.test.ts` "stops mid-stream without delivering anything further" | `dispose()` while frames are queued; asserts no further frames, no state churn, reader cancelled |
| Unmount mid-stream (node deleted) | `agent-sse-node.test.ts` "aborts the request and cancels the reader" | `_onNodeDeleted()`; asserts `AbortController.abort()`, reader cancelled, 0 pending timers, later frames never arrive |
| Unmount **while reconnecting** | both suites | dispose during the backoff window; asserts `hasPendingTimer()` false and the timer map empty |
| Network drop and recovery | "reports the drop, backs off, and recovers" | reader rejects → `reconnecting` + `onError` + `retryCount` 1 → run the timer → second stream delivers → `retryCount` back to 0 |
| Backoff curve | "doubles the delay across consecutive failures" | 1000 → 2000 → 4000 |
| Server closes the connection | "goes to closed and schedules nothing, by default" | EOF → `closed`, no error, no timer |
| Server closes, resume opted in | "reconnects on a clean end when asked to" | `reconnectOnStreamEnd: true` → `reconnecting`, no error reported, second fetch issued |
| Unterminated final event at EOF | "dispatches a final event the server did not terminate" | the spec discards it; we dispatch it, because real servers just close |
| Cancel in flight | "cancels a request that is still in flight" | `disconnect()` before the fetch resolves; the late response delivers nothing |
| Rapid open/close cycles | both suites | 5 connect/disconnect pairs then a connect: 6 fetches, 5 aborted, one live; node-level version does 10 cycles via signal edges |
| Terminal vs retryable HTTP | "treats a 4xx as terminal and a 5xx as retryable", plus a 429 case | 404 → `error`, no timer; 503/429 → `reconnecting` |
| Retry budget exhausted | "stops at maxRetries and says so" | `error` with a message naming the budget |
| `autoReconnect: false` | "does not retry at all" | single failure → `error` |
| Duplicate suppression after resume | "resumes with Last-Event-ID and suppresses the replay" | asserts the `Last-Event-ID` request header **and** that the replayed id is dropped once |
| Dedupe off | "delivers the replay when dedupe is turned off" | both copies delivered, semantics string changes |
| Server `retry:` field | "honours a server retry: field" | 250 ms wins over the configured 1000 |
| EventSource self-retry | "reports the browser's own retry without opening a second stream" | `readyState` 0 → `reconnecting`, **one** EventSource, no timer of ours |
| EventSource gives up | "takes over with its own backoff" | `readyState` 2 → our timer → second EventSource |
| Missing platform API | two cases | no `fetch` / no `EventSource` → `error` naming the missing API, not silence |
| Base-class teardown | node suites | a delete listener registered via `addDeleteListener` still runs, i.e. the `Node.prototype._onNodeDeleted` super call is present |
| Parser boundary safety | `agent-stream-parsers.test.ts` | one-character-at-a-time drip feed; JSON document cut at every index |

## What is **not** verified

Be sceptical of anything below this line; none of it has been run.

1. **No live run against a real streaming endpoint.** Every transport test uses an injected
   double. The fetch transport has never spoken to a real server, so the response-shape
   assumptions (`res.ok`, `res.body.getReader()`, `TextDecoder` streaming) are only as good
   as the doubles. This is the single biggest gap.
2. **Never opened in the editor.** No node has been placed on a canvas, no port has been
   seen in the property panel, and the new `Streaming` picker subcategory has not been
   looked at. Port groups, tooltips and enum labels are unreviewed by eye.
3. **`TextDecoder` is used unguarded-ish** — `typeof TextDecoder !== 'undefined'` decides,
   and if it is absent and the transport yields `Uint8Array`, chunks decode to `''`
   silently. Never exercised, because the doubles yield strings. A real browser always has
   it.
4. **The value-before-signal ordering claim is reasoned, not proven end to end.**
   `flagOutputDirty` → `sendValue` → `queueInput` appends to a per-input array that the
   downstream node drains in key-insertion order (`node.ts:475`), so `data` lands before
   `onMessage`. No test wires two real nodes together to confirm it; the utility-node tests
   set the value input and pulse the signal in that order by hand.
5. **`withCredentials`, CORS, and cross-origin behaviour**: untested.
6. **Large-payload and long-run behaviour**: the spec asks for >1 MB messages and 1000+
   message stability. Not measured. The caps exist and are tested; the performance claim is
   not made.
7. **The SSE parser re-scans an unterminated frame on every chunk.** O(n²) for a single
   enormous event. Fine for normal frames, unmeasured for pathological ones.
8. **No jitter on the backoff.** Deliberate (deterministic tests), but a fleet of clients
   reconnecting to a restarted server will thunder. Worth adding with an injectable RNG.
9. **The example graphs pass the static validator, not a runtime.** `catalog:examples` is
   green, which checks node types, port names and connection compatibility — it does not
   run them.
10. **AIX-005's "example agent chat project"** is not built. The catalog example
    `agent-sse-chat-stream` is the wiring, not a project, and a real one wants AGENT-002/003
    too.
11. **`docs/nodes/data/sse.md`** and the stream-utilities doc page are not written.
