Nothing here treats "connection dropped" as a distinct case from "stream finished" — the graph only reacts to `connectionState` changes for display, and to `onOpen`/`onClose` for logic. Walking through what's wired:

**While it's down and retrying.** [Server-Sent Events](noodl-node:1346ccf9-0dec-4fd8-8ea9-d052bc9559ee) has `autoReconnect: true` and `maxRetries: 5`, so a dropped connection moves into backoff and retries automatically (exponential, capped by `maxReconnectDelay: 8000`). You'd see this live: `connectionState` drives the [Connection value Text](noodl-node:51d9f785-9054-4d22-89b0-e29750ee0f32) (it'll read "reconnecting"), and `retryCount` drives the [Retries value Text](noodl-node:c9b7311b-b36f-468b-862a-ff08c132cd3d). The in-progress answer [Text](noodl-node:0f4958bf-b423-49c6-88cc-8c75d011d525) is bound to `connected`, and per the SSE node's own docs `connected` is false "during connect, backoff and after a terminal failure" — so the partial answer disappears from view while it's retrying, even though the text itself is still sitting in the [Text Accumulator](noodl-node:cef7f30c-f86f-4a03-847b-948157c265a2).

**If it reconnects successfully.** `onOpen` is wired straight to the accumulator's `clear` signal. So a successful reconnect wipes whatever partial answer had accumulated before the drop, and the visible answer starts over from empty as new chunks arrive. There's nothing in this graph that stitches the pre-drop text and post-reconnect text together.

**If retries run out.** After `maxRetries: 5` failed attempts, the SSE node's own docs say the connection reports a terminal error — `connectionState` becomes "error", `lastError` gets a message, which shows in the [error Text](noodl-node:6bb80468-1830-4f4b-8a5d-626612aed321). Critically, `onClose` "fires when the stream stops, whether cleanly or with a terminal error" — this graph does not distinguish the two. So the same two handlers that normally save a completed answer also fire here: [Function](noodl-node:aa8d77d0-863a-4bf8-8b97-f195c975a2b9) takes whatever is currently in `accumulated` (i.e. the partial, cut-off answer) and appends it to `messages` as if it were the finished reply, via [Set Global Store](noodl-node:e1c8126a-ae12-4dd7-81df-32efc93208de); simultaneously the same partial text is written to the `answer` key by [Set Global Store](noodl-node:447caf2a-2074-4fdf-8025-87d8c4a80ee6). So a terminal drop mid-answer ends up committing the truncated text to the transcript as a normal message, with no marker distinguishing it from a clean completion.

One thing I can't answer from this slice: whether a mid-stream drop actually resumes from where it left off (using `Last-Event-ID`, mentioned in the SSE node's docs for the Fetch transport) or restarts the request from scratch — that depends on the endpoint's behavior, which isn't part of this graph.
