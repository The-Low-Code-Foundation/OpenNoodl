## Bug list:

1. Clicking "explain this node" is actually a great feature now that we have a chat we can use to discuss with an LLM and get advice about a particular node. What's needed to make it truly useful for beginners is:
* Be able to ask about a node's configuration AND its current input and output signals and values. Right now when I said 'why is the output value null?' it wasn't able to detect and explain
* This would also then be a good opportunity to allow the 'explain this node' to dig around in the nodes connected to the one you've selected, or even drag select a group of nodes to get it to explain multiple ones simultaneously. 
* Can the explainer also dig into 'components' that are on the node canvas? So instead of just seeing the component node config and input / output values, it can also see how that component is built internally, what nodes it contains, to give a more detailled answer.
* Typing into the single line input at the bottom is hard: you can't use backspace, you can't see new lines, it's just one line of text. It should be a multiline input with regular typing actions.

1bis. This is a problem app-wide, but I'll put it in the context of explain this node: The output text in the chat (same for the builder panel, and all other panels and especially editor / launcher modals) isn't clickable, so if the agent recommends a link to something, the user can't click it, can't select it to copy and paste, they're stuck typing it out by hand. 

2.  The Visual Function (Blockly) node is missing a few blocks I think. I wasn't able to use a Number() operator for example to turn a string into a number. There's no log block. 

3. The Visual Function node has a lot of visual errors. For example the dropdowns that appear on certain nodes have strange highlight colours, between the one selected and the other non selected ones, their hover animations make them very hard to read. We should rename 'Runtime Variables' to 'App variables' to show they're the global ones Noodl.Variables.etc. Can you maybe list out any other blocks you think it might be missing to really make it a contender against the regular function node?

4. When asking the internal AI to build me stuff, I asked it for a simple function that would take a string, cut off the first character, then convert it to a number and multiply by 0.9. It made a Script node inside a component for this, which is overkill but it also didn't code it right, it didn't add any input or output signals, which means the Script can't be run (it doesn't run on value changes). I asked it to replace it with a Function node, which it did successfully, but it used like var foo = "bar" type code instead of more modern const / let, and used a complex regex function instead of a simple splice, so I think the AI is still struggling with Noodl standards. We want the user to be able to read the resulting code and learn from it if they want to. P.S. The component it created me that had a script and then a function, it said 'target port doesn't exist' from the component input to the function node port, and when I deleted the connection and redid the exact same connection, it was fine. So I think the AI created a faulty connector, the ports were all created fine, just the connector that wasn't wired correctly for some reason between the function and component inputs / outputs.

5. This may be a bug with my setup from so many dev sessions, but I clicked the 'Connect MCP' in the launcher, and it threw an error about already being connected, fine. Then I opened a NodeGX project folder in VSCode with Claude Code extension, asked it to add something to the project, and it complained constantly about the MCP being bound to a different project and that it had to make a workaround to get access to the project open in VSCode. It worked in the end, but I wanted to flag that bug in case it's a global one and not limited to my machine. 

6. Can we deepen our fix on the left menu we made where the default width of component menu and node props is the same? We left it that the user could still widen the menu widths themselves, so if they do there's still a jump in the node canvas as it resizes clicking on of off nodes, which happens very frequently in daily use. Can we make it that if the user resizes one of either component or node menu, that BOTH inherit the size they've chosen? In both directions. So there's no more jumping apart from the other less used panels. 

7. When I open the node picker and search 'CSS', the search results start offset Y downwards, so you don't see the CSS result unless you manually scroll up the search results to see it.

8. The component bench is an amazing addition, but absolutely full of bugs:
* All node bench components open at a fixed height of like a couple of hundred pixels, which makes them all look very silly. We need to let users define some kind of 'default width and height' of each component, with the ability to increase and decrease width and height in the bench. 
* When you save a 'scenario' and select it, you can't clear it to return to 'no scenario' values
* The 'data' option doesn't seem to work at all, throws weird messages and buttons all over the place, see screenshot 'workbench-1'. I think allowing the user to add dummy data should just be the default, forget signing in and signing out and real database data for now, maybe à la limite let the user 'import' a record from the database to use as dummy data in the component inputs, but let's remove all the 'sample data' 'real backend' stuff, it's insanely confusing. Just let the user define the inputs and outputs, done. 

9. When the MCP or AI builds something with visual and logic nodes, it seems to tend to put all nodes in the same central column, so afterwards you have to drag the logic nodes out to the left or right or the central visual node column, as you would normally do when building in NodeGX. 

10. We need to ressurect the phase 9 style overhaul project, bring it up to date with the new editor and rescope. It'll help both the user and the AI if we have proper style tokens we can use throughout the app, so we can set what the primary and secondary colours should be, what we expect cards to look like in terms of shadows, hover actions, etc. This is probably bigger than the original phase and requires good brainstorming (for example, do we go as far as making logic components that have outputs to connect to groups etc. that will provide the user's preferred animations to that visual element, like pulsing when hovered etc?). This will also facilitate importing components from one project to another, where in the origin project they had style token 'main group' which had certain colours that don't apply to the new project, but the importer could use the style token system to make the equivalents and present the changes to the user during the import, or something. 

11. On the function node, why can't we add signal outputs to the props panel of the function node, when we can add multiple output signals inside the code itself?

16. One idea that was surfaced for the AI builder, both Claude Code and internal builder: Why don't we have a CLAUDE.md file at the level of each individual project, and a global CLAUDE.md file at the editor level? The global one gives context that builds up as the user progresses through their experience building with NodeGX and AI, becoming like a personality and preferences document, a learnings document, a 'gotchas' document, for global issues. The project level one learns about what the user likes and dislikes in that individual project, the style and objectives, the evolution of the scope, etc. This is a big chunk of my https://ai-coding.visualhive.co guide, where I list out all the basic docs a project should normally have if being built by AI, like learnings, instructions, architecture, roadmap, gotchas, etc. At the global level I'm open to ideas. But I think this would provide the extra context needed to let the user have their NodeGX AI 'get to know them' and their way of developing, their experience level, do they prefer Function nodes or Visual Function nodes? Are they building for fun or trying to create production apps? What deployment target do they tend to prefer? Do they have a go-to backend? etc etc.
