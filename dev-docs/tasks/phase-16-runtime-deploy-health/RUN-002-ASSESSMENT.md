## 3. The three real gaps (what the weeks actually go to)

### 3.1 Hydration is broken by the React upgrade — a bug, not missing work

`renderDeployed` decides hydrate-vs-createRoot like this (`noodl-viewer-react.js:60`):

```js
if (element.children.length > 0 && !!element.children[0].hasAttribute('data-reactroot')) {
  currentRoot = ReactDOM.hydrateRoot(element, this.createElement(...));   // SSR path
} else {
  currentRoot = ReactDOM.createRoot(element);                            // CSR path
}
```

`data-reactroot` is a **React ≤17** marker. **React 18+ `renderToString` no longer emits it** — empirically confirmed: the SSR output from the React 18.3.1 server contains no `data-reactroot` anywhere. RUN-001 moved the runtime to vendored React **18.3.1** (default) with a **19** opt-in. So *post-RUN-001, this detection always fails*: the client falls into `createRoot` and **re-renders the whole app from scratch, discarding the server HTML instead of hydrating it.**

Consequence: SEO/first-paint benefits (content is in the HTML) are unaffected, but there is no hydration — a double render, and the "hydrate cleanly without mismatches" success criterion cannot be met until the detection is fixed. This is the RUN-001 pattern repeating: a latent defect the version upgrade exposed, invisible until you actually run the path.

**Fix shape (small, early win):** stop depending on a marker React removed. Have the SSR server stamp the root it rendered (e.g. `<div id="root" data-ssr="1">…`) and have `renderDeployed` hydrate on that, or on "root already has children" alone. Must be verified with an actual browser (hydration-mismatch warnings only surface at runtime), reusing the RUN-001 CDP corpus harness.

> **Update (2026-07-25, verified in a browser — not a cheap win after all).** I made the detection change (SSR server stamps `data-ssr="1"`; `renderDeployed` hydrates on it) and drove it through headless Chrome with the *development* React build (production suppresses mismatch warnings). Result: the client took the hydrate path (`hydrateRoot` called, `createRoot` not) with **no** React mismatch warning — but the DOM ended with **two** `#root` children: the server's div (1013 chars of markup) *plus* a second, client-fresh div (699). Same duplication under the production build. **Root cause:** the deployed runtime loads the root component **asynchronously** (bundle fetch), so `hydrateRoot`'s first synchronous render is `null`; React adopts the empty tree, and when the real content arrives it mounts as a *duplicate* beside the orphaned server DOM. So the naive flip is **worse than the status quo**. Real hydration needs a **synchronous first render** — the root component and its bundle resolved before `hydrateRoot` — which is a genuine RUN-002 deliverable, not a one-liner. **Landed instead:** `renderDeployed` was made an explicit, safe `createRoot` (verified: single `#root` child, server markup cleanly replaced — this is also what shipped all along, since the `data-reactroot` branch was dead) with the finding documented in-code; the SSR server keeps stamping `data-ssr="1"` as the signal the eventual hydration slice will use.

> **DONE (2026-07-25, slice 2 — real hydration, browser-verified).** `renderDeployed` now detects `data-ssr="1"` + non-empty `#root` and runs an async **pre-hydration settle** that mirrors the SSR server's render sequence exactly before calling `hydrateRoot`: create the runtime → `ssrSetupRuntime` (now returns the `setData` promise; awaited) → `triggerDidMount` → `settle()` with a `window.fetch` in-flight tracker (temporarily installed, restored before hydration) → `SSR_PageLoading`/`SSR_PageReady` gate → settle again → `hydrateRoot` with the settled tree as the synchronous first render. The settle/gate/fetch-tracker machinery is shared with the server (`static/ssr/render-gate.js`, `createFetchTracker` added; the server template's inline counter replaced with it). **The double-didMount hazard this creates was found and guarded:** during hydration a node's didMount fires once via `triggerDidMount` (pre-settle) and would fire again when React commits — `NoodlReactComponent.componentDidMount` now skips the signal when `didCallTriggerDidMount` is set (cleared on unmount so genuine remounts fire normally), and Router/Page Stack `props.didMount` are idempotent-while-mounted (they were registering twice in RouterHandler). Any pre-settle failure falls back to the old `createRoot` path. **Verified in headless Chrome (dev React for mismatch warnings, plus a production-React run):** `hello-world` dev+prod, `probe-router` `/` and `/second`, and the gated 400 ms-async-data project all show `hydrateRoot` called / `createRoot` not, a single `#root` child, **the server-rendered element adopted by identity** (`firstElementChild` preserved across hydration), zero hydration warnings — and the gated page's first client render *contains* the late-arriving data because hydration waited for the client-side replay through the same PageReady gate. **Interactivity:** clicking "Go" on the adopted DOM navigates client-side (no reload) with correct title/content; `history.back()` shows a pre-existing router quirk (empty content after back-nav) that reproduces identically in pure CSR — behavior parity, not a hydration regression. CSR control (no `data-ssr`) still takes `createRoot` and renders identically. **Caveats that remain open:** no state serialization — hydration *re-runs* the graph's async work client-side (data fetched twice: once per side; nondeterministic nodes can still mismatch), XHR-based fetches aren't tracked by the idle counter (same gap as the server), the server still renders with React 18.3.1 regardless of a project's react19 opt-in (§3.4 skew), and URL query strings aren't passed to the server-side router (server settles with `search: ""`).

### 3.2 SEO injection is an unfinished TODO — the headline benefit isn't delivered end-to-end

`static/ssr/index.js:163` is `// TODO: Inject Noodl.SEO.meta`. The `<title>` in the rendered output is the **static template title**, not the value a project sets via `Noodl.SEO.setTitle`/`setMeta`. So the server never writes SEO into `<head>`. For a feature whose entire justification is SEO and social previews, this is load-bearing.

> **Update (2026-07-25 — the injection was the easy half; the runtime doesn't populate SEO server-side).** I implemented the head injection (read `globalThis.Noodl.SEO.title`/`.meta` after render, replace `<title>`, splice `<meta>` before `</head>`; 14/14 unit tests incl. XSS escaping) and ran it end-to-end against `hello-world`, which has a Router + a Home page whose Page node carries `title: "Home"`. The served `<title>` **stayed the template default** — and instrumenting the server showed why: at injection time `Noodl.SEO.title === ""` and `.meta === {}`. **The runtime never populates SEO during server render**: the client sets `document.title` to "Home" (router navigates, `router.tsx:323` fires), but server-side the router does not complete its initial navigation, so `SEO.setTitle` never runs. This is the same "page router SSR is unfinished" gap (`static/ssr/index.js` `// TODO: Maybe fix page router`; the router's initial route resolution sits behind `typeof window !== 'undefined'` guards, `router.tsx:81-91`). So SEO end-to-end needs the **producer** side — server-side router navigation populating SEO — before injection means anything. **Landed anyway:** the injection helper (`injectSeo`) is correct, tested, and no-op-safe (returns the HTML unchanged when SEO is empty), so it is the ready consumer for when the producer is fixed. `setOpenGraph`/Twitter/structured-data remain additive on top.

> **Correction + FIX (2026-07-25, slice 1 — SEO now works end-to-end).** The update above misdiagnosed the cause. Instrumenting `setTitle` with stack traces (not just reading the value) showed the runtime **does** populate SEO server-side: the router registers via `triggerDidMount` → `_registerRouter` → `reset()` (none of which is `typeof window`-guarded; lines 81-91 only guard the *popstate listener*), `resetAsync` navigates to the start page, and `setTitle("Home")` fires. `Noodl.SEO.title === "Home"` **immediately before `renderToString`**. It reads `""` **immediately after**, with *no* intervening `setTitle` call. Root cause: `renderToString` constructs the `Viewer` component, whose **constructor re-runs `NoodlJSAPI`** (`viewer.jsx:147`), and that unconditionally did `global.Noodl.SEO = new SeoApi()` (`noodl-js-api.js:23`) — a **fresh, empty instance that clobbered the one the runtime had just populated**. The double-init is SSR-specific: `ssrSetupRuntime` calls `NoodlJSAPI` once (SEO #1, gets the title), then `renderToString`'s Viewer ctor calls it again (SEO #2, empty) before `injectSeo` reads it. **Fix (landed):** (1) `noodl-js-api.js` makes SEO idempotent (`global.Noodl.SEO = global.Noodl.SEO || new SeoApi()`) so the second call preserves the populated instance; (2) `SeoApi.reset()` added and the SSR server calls it at the top of each `buildPage`, so the reused per-process singleton can't bleed one page's title/meta into the next; (3) `injectSeo`/`escapeHtml` extracted to `static/ssr/inject-seo.js` (committed, unit-tested — 10 cases) so the ship logic is no longer trapped in an untestable template; `SeoApi` buffering + reset covered by `tests/seo-api.test.ts` (6 cases). **Verified against the real SSR runtime bundle** (`webpack.ssr.prod` → `noodl.deploy.js`, assembled + esbuilt + run): `hello-world` serves `<title>Home</title>` (was `Hello Preview`); a meta-bearing variant serves the injected `<meta name="description">` + `<meta name="og:title">`; `probe-router` serves `<title>Home</title>` on `/` and `<title>Second</title>` on `/second` with no cross-request bleed; headless-Chrome check shows the client `document.title` also resolves to `Home` with no hydration-mismatch warnings and a single `#root` child. So the SEO benefit — the feature's whole justification — is now delivered end-to-end for the router/SEO cases exercised. **What this changes about the plan:** the §6 slice-1 "producer" work turned out to be a one-object-lifetime bug, *not* the server-side-router rewrite predicted. The busy-loop → `SSR_PageReady` swap (still fragile, still worth doing) and data-dependent rendering (§3.5) remain genuinely open; §3.3 (node server-compat) is untouched and remains the crux.

### 3.3 Node server-compatibility is unhandled — the spec's named crux, confirmed

The router probe surfaced it immediately: a JavaScript/Function node running `window.__probe = …` throws **`ReferenceError: window is not defined`** server-side. The runtime catches it ("Error in JS node run code") so the render *survives*, but that node's logic **silently does not run on the server** — a partial render the user didn't author and can't see. `window` is deliberately left undefined (so the runtime's own `typeof window !== 'undefined'` guards take the server branch), which means any *user* node code touching `window`/`document`/browser globals breaks.

Nothing classifies nodes as server-safe / adaptable / client-only (Step 2, unstarted), and there is no mechanism to defer a client-only node to hydration rather than letting it throw. This is where the genuine multi-week effort lives, exactly as the spec predicted — the render engine was never the hard part.

> **DONE (2026-07-25, slice 3 — full node audit, catalog classification, client-only deferral; all verified e2e).** Every registered node type was audited for browser-API usage in its *load path* (initialize, setters, output getters, lifecycle — the code that actually runs during a server render; interaction-driven signal handlers never fire server-side and don't count), including `nodes-deprecated/`, which the first audit sweep missed.
>
> **Classification schema (shipped structurally, one source of truth):** a node definition may declare `ssr: { compat: 'safe' | 'partial' | 'client-only', note? }` (typed in `@noodl/types` `NodeSSRCompat`; absent = audited-safe). `defineNode` copies it to metadata, `createNodeFromReactComponent` forwards it (same passthrough DEBT-006 added for `deprecated`), and the catalog generator emits `ssr` on **every browser-available node** (cloud-only types omit it — the axis doesn't apply). Flows automatically into the enriched catalog, `CatalogNode`/`EnrichedCatalogNode` typings, and the MCP `get_node_type` detail. Result: **119 safe / 9 partial / 4 client-only** across the 132 browser types. Client-only: Screen Resolution, Open File Picker, Gyroscope, Script Downloader. Partial (note explains the caveat): Delay, States, Animate To Value, Animation, Transition (all frozen-clock — TimerScheduler never advances server-side), Page Stack (URL/history sync browser-only), User (sessions live in browser storage → always logged out server-side), Function + Script (user code touching window fails server-side, logged, outputs unchanged). SCHEMA.md documents the field.
>
> **Client-only deferral (the degrade-don't-throw mechanism):** on the SSR server — detected via `platform.isSSRServer`, set *only* by the windowless branch of `createArgs()` in noodl-viewer-react.js; "no window" alone is NOT the signal because the cloud runtime is also windowless and must run nodes for real — `defineNode`'s factory creates a `client-only` node **inert**: ports registered so connections resolve, input defaults applied, but initialize skipped, setters no-ops, outputs read `undefined`, dynamic-port registration accepts anything without running author code, `nodeScopeDidInitialize` suppressed. One `console.warn` per type + a per-page summary in the server log naming the deferred types (`context._ssrDeferredNodeTypes`). The browser never defers — the node runs normally after hydration. 6 unit tests (`test/ssr-client-only-deferral.test.ts`). **Trap found on the way:** `NoodlRuntime`'s constructor copies a fixed allow-list of platform fields (`requestUpdate`, `getCurrentTime`, `webSocketOptions`, `objectToString`) — `isSSRServer` had to be added there or the flag silently never reaches node creation (first smoke run proved this: the deferral didn't engage and Open File Picker crashed the render exactly as before).
>
> **Guard fixes landed with the audit (adaptable → actually safe):** Page Stack didMount/willUnmount/`_updateUrlWithTopPage` (was the *guaranteed* SSR crash — unguarded `window.addEventListener` in a didMount that `triggerDidMount` invokes on every server render) plus `window.location.search` → bare `location` (the server shims `globalThis.location`, which is how Router already worked); Router willUnmount/`_updateUrlWithTopPage`/`window.open`; **REST2's browser-detection** (`typeof _noodl_cloud_runtime_version` conflates "not cloud" with "browser" — SSR took the browser branch and threw on `new window.XMLHttpRequest()`; now `typeof window`, so SSR/cloud both take the fetch path — same latent misclassification exists benignly in `dbmodelcrudbase.js`/`user.js` where the browser branch only touches polyfilled localStorage); `controls/utils` stylesheet injection (both current and deprecated copies — Text Input's `placeHolderOpacity` setter reached it at load); transitions' `window.performance.now()` (server completes transitions immediately); RouterHandler's `window.Noodl` → `globalThis.Noodl`; Navigate To Path + External Link action no-ops.
>
> **Verified end-to-end against the freshly built `webpack.ssr.prod` bundle:** (1) a hello-world variant with Screen Resolution → Text and an Open File Picker — previously **fatal at graph load** (`document.createElement` in initialize → CSR fallback) — now serves full HTML with title, content, and both types named in the server log; the width-bound Text serves its default. (2) `probe-pagestack` (Component Stack + transitions) — previously the guaranteed crash — now serves 8.7 KB of real markup ("STACK-A", "Push") **and hydrates cleanly in headless Chrome** (hydrateRoot called, no createRoot fallback, zero mismatch warnings). (3) Regression: hello-world and probe-router still serve correct titles/content on both routes. Harness note for reuse: the deploy `index.js` bootstrap is **project-specific** (`{{#export#}}` spliced) — reusing another project's produces bundle-fetch failures that masquerade as hydration mismatches.
>
> **Known caveat, now observed concretely (the next hydration slice):** a client-only node whose *output feeds visual content* (the Screen Resolution → Text case) still breaks hydration adoption: the server serves the default ("unset"), the client pre-settle runs the node for real ("756"), React 18 hits the text mismatch outside any Suspense boundary and **recovers by discarding the server DOM and client-rendering the whole root** — degraded (CSR-equivalent, page works) but not adopted. Fix shape: defer client-only nodes during the hydration pre-settle too, then activate them after `hydrateRoot` commits (the useEffect pattern) — requires re-applying their parameters on activation, which is why it didn't ship in this slice. Client-only nodes that don't feed the initial render (file pickers, sensors) hydrate unaffected.
>
> Also fixed en route: `catalog:merge` had been silently broken since DEBT-006 deleted For Each Actions' dead itemAction mechanism (its `runtimeBehavior` enrichment claimed dynamic ports the node no longer has; the structural catalog had been regenerated twice without re-running merge). Enrichment updated, both `catalog:check` and `catalog:merge:check` green again.

### 3.4 Secondary: version skew + fragile trigger

- The SSR server pins **React 18.3.1** and renders with it regardless of a project's `runtimeVersion: 'react19'` (the bundle externalizes React to the server's node-module copy). Combined with §3.1, react19 projects also never hydrate, and could hit 18-vs-19 SSR semantic differences. Decide: does the SSR server track the project's chosen React pair?
- ~~The render trigger is a 1000-iteration `triggerDidMount`/`_doUpdate` busy loop (`static/ssr/index.js:147`) because `SSR_PageReady` is commented out.~~ **FIXED (2026-07-25 — busy loop replaced by settle + PageReady handshake).**

> **Update (2026-07-25, busy-loop swap DONE).** The render trigger is now principled, in a committed, unit-tested module (`static/ssr/render-gate.js`, 12 tests in `tests/ssr-render-gate.test.js`):
> 1. **`settle(runtime)`** waits for real quiescence instead of spinning 1000 times: `runtime.updateScheduled` is the runtime's own "work pending" flag (server-side `platform.requestUpdate` is `setImmediate`, so scheduled updates fire on their own while settle yields — it observes, it doesn't drive), plus an `isIdle` predicate the server wires to an **in-flight-fetch counter** around its `globalThis.fetch` shim, so bundle loads *and any data fetch* hold the render. Quiet-turn ticks are `setTimeout`-based so a fast microtask spin can't exhaust the quiet budget while I/O is pending. `triggerDidMount` is re-run each turn (idempotent per node) so components arriving from async bundle fetches get mounted. Hard cap (`maxTurns`) for graphs that never go quiet (looping animations) → renders current state with a warning.
> 2. **`createPageReadyGate(...)`** implements the original team's intended SSR_PageLoading/SSR_PageReady handshake, now actually functional. **`onPageReady` is enabled on the Page node** (`page.ts` — the "TODO: Enable with SSR" block, typed, group "Server Side Rendering"; node catalog regenerated). A page with the signal connected announces SSR_PageLoading; the server holds the render until the graph fires Page Ready or a timeout (`NOODL_SSR_PAGE_READY_TIMEOUT`, default 10 s) passes — timeout renders current state and names the culprit page node in the warning.
>
> **Two latent bugs in the unshipped protocol, found and fixed:** (a) the server template listened for SSR_Page\* on `noodlRuntime.eventEmitter`, but pages emit on `noodlRuntime.context.eventEmitter` — a different object; the original server could never have heard a page. (b) The announce lived in Page `initialize` gated on `isInputConnected('onPageReady')` — but `NodeScope.setComponentModel` creates all nodes (running initialize) *before* wiring any connection, so the check was always false and SSR_PageLoading could never fire. Moved to the existing `nodeScopeDidInitialize` lifecycle hook, which runs after connections are wired.
>
> **Verified end-to-end** against the freshly built `webpack.ssr.prod` bundle (same harness as slice 1): `hello-world` serves in ~64 ms (title + content + `data-ssr` stamp intact), `probe-router` serves both pages with correct titles (multi-bundle fetch held by the idle counter). The new **gated corpus variant** (`stage-gated`: Home page + JavaScriptFunction that awaits 400 ms, sets a text output, fires `Outputs.done()` → Page `onPageReady`) serves in ~460 ms **with the late-arriving text in the server HTML** — the render provably waited for the graph's ready signal. With `NOODL_SSR_PAGE_READY_TIMEOUT=100` it renders at ~170 ms *without* the late content and logs `SSR: page(s) never signalled Page Ready for / within 100ms: home_page`. Full viewer-react jest green (33/33). This also delivers the *mechanism* for §3.5 (fetch-held render + graph-signalled readiness); what remains there is validating real query nodes against it.
>
> **Trap for the next slice:** server-side `platform.getCurrentTime` is `() => 0`, so TimerScheduler time never advances — a **Delay node can never fire its Finished signal server-side** (and a running timer keeps `hasPendingTimers` true). Don't use Delay to drive `onPageReady`; async JS (setTimeout is native in Node) and data fetches work fine.

### 3.5 Data resolution before render — not yet exercised

Neither smoke project fetches remote data, so server-side data resolution (spec Step 5) is untested here. The graph *does* know a page's query dependencies (a real advantage), and the SSR server already polyfills `fetch`/XHR, but "wait for data before renderToString" is not implemented beyond the busy loop. This remains genuine work and should be measured against a data-dependent corpus project next.

> **Update (2026-07-25):** the busy-loop swap (§3.4 box) delivers the *mechanism*: the render is now held while any `fetch` is in flight (in-flight counter → settle's `isIdle`) and until explicitly-gated pages signal Page Ready — the gated smoke test proves async-arriving data lands in the served HTML. Still open here: exercising real **query/data nodes** (which may use XHR rather than fetch — the counter doesn't cover XHR yet), and deciding whether common data nodes should auto-gate rather than requiring the user to wire `onPageReady`.

## 4. Traps found (for whoever implements)

- **Bundles must sit at the deploy *root* `./noodl_bundles/`, not only `public/`.** The server-side fetch shim (`static/ssr/index.js:42`) reads `'.' + args` (cwd-relative). `express.static('public')` serves the browser copy. The design doc's "static assets → `/public`" step alone would leave the *server* unable to find bundles → every multi-bundle project would silently CSR-fallback. The real deploy flow must write bundles to both, or fix the shim. (My harness writes both; that's why multi-bundle rendered.)
- **`renderToString` output has no `data-reactroot` under React 18/19** — see §3.1. Any code keying off it is already dead.
- **`window` is intentionally absent server-side**, not polyfilled — the runtime's SSR guards depend on that, so you cannot "just define window" to fix user nodes; classification + deferral is the answer.
- The SSR server's own `package.json` still declares React `^18.3.1` while the client can opt into 19 — keep these in lockstep or the skew in §3.4 compounds.
