The side panel, reconsidered

Six real defects, one structural idea, and a per-panel restyle. Everything below is built on the UIX-001 tokens already in colors.css — same azure accent, same coral brand dot, same light/dark ladder. The editor window in the next section is live: click the rail, drag the divider, switch modes.

What's actually wrong

Two of these are bugs with a single root cause each — worth fixing before any restyle, because they're why the panel feels broken rather than just plain.

Settings panels get squeezed instead of scrolling

Bug

The last section's help text is clipped mid-sentence and the panel appears to end early. Cause: collapsable sections are flex children with overflow: hidden and no flex-shrink: 0, so when the content is taller than the panel the sections compress — the scroll container never overflows, so it never scrolls. Fix is one line: flex: 0 0 auto on every direct child of the scroll area.

noodl-core-ui/src/components/sidebar/CollapsableSection/CollapsableSection.module.scss:1

Every panel is 34px taller than the space it sits in

Bug

BasePanel .Root sets height: 100% plus 16px padding and a 1px border — and the editor has no global box-sizing: border-box, so the box is 34px taller than its slot and the ancestor's overflow: hidden eats the bottom. This is the "couple of dozen pixels" and it happens on every screen height, not just 13-inch.

noodl-core-ui/src/components/sidebar/BasePanel/BasePanel.module.scss:1

Drag-selecting text past the panel edge cancels the gesture

Friction

A click event fires on the common ancestor of mousedown and mouseup — so a drag that starts in a panel field and ends over the canvas produces a click whose target is <body>, and every "clicked outside → close" rule in the popup layer treats it as an outside click. Fix: decide on pointerdown, act on pointerup, and check the pointerup target too — or capture the pointer for the duration of the drag, which is what the divider in the prototype below does.

noodl-editor/src/editor/src/views/popuplayer.ts:320

The panel can never be narrower than 380px, or wider without a drag

Friction

SideNavigation .Root hard-floors the whole rail+panel at min-width: 380px, so the divider's sizeMin={200} never applies. There is no collapse, no snap, no keyboard shortcut, and no per-panel memory — one width serves the 240px-wide component tree and the 560px-wide backend card alike. Hence the constant manual resizing.

Width belongs to the panel

Components wants ~280px. Backend Services wants ~560px. Storing the width against the panel id and restoring it on switch removes most of the resizing entirely — switch the panel, get the right width. Try clicking through the rail with the readout visible.

Wide is a toggle, not a drag

⌘\, the header button, or a double-click on the divider snaps to min(760px, 55vw) and back to the panel's own width. The topology panel already does exactly this by hand at 55vw; this generalises it instead of special-casing one panel.

Floating for the panels you watch

Explain, Build and the data browser are read-while-you-work panels. Floating puts them over the canvas, draggable by the header, so the graph stays where you left it. Position is remembered per panel.

Full replaces the portal hack

Data, Schema and Permissions already go full-screen today — via position: fixed overlays rendered through createPortal from inside a card. Making Full a panel mode means one code path, an escape route, and a rail that still works.

One panel, any width

If the panel's width is going to move constantly, panel content has to be width-aware — and it can't be the window's width that decides, because the panel is a fraction of it. Container queries on the panel body give every panel three layouts for free. Below is the same Backend Services panel at three widths; note the action row and the label columns. The header is a container too — under 360px it keeps only widen and hide, and Float and Full move into ⋯ rather than squeezing the panel title down to "Compo…".

What I'd build, in order

The first two steps are small and fix things that are actively wrong. Nothing after that depends on agreeing to the whole mode system — each step stands alone.

Step 1

Make panels scroll

box-sizing: border-box on the panel root, min-height: 0 on the flex chain, flex: 0 0 auto on every direct child of a scroll area, 32px of bottom padding inside it. Replace the stale overflow-y: overlay (a Chromium alias for auto now) while in there. Two files, and the bottom-cut-off and mid-sentence clipping both go.

Step 2

Stop the popup layer treating a drag as an outside click

Gate the outside-close rules on the pointerup target as well as the pointerdown one. Fixes drag-selecting text out of the panel, and the same gesture in every popout and dialog.

Step 3

Panel width: per-panel memory, a wide toggle, and a real collapse

Drop min-width: 380px so the divider's own 200px floor applies. Persist width per panel id in editor settings; add ⌘\ / double-click-divider to snap wide and ⌘B to hide. Retire the topology panel's hardcoded 55vw special case in EditorPage.tsx — it becomes "this panel's remembered width is wide".

Step 4

Container queries, one shared row component

container-type: inline-size on the panel body, three breakpoints, and one <PanelRow label> that every panel uses instead of hand-rolled grids. Fixes the backend action overflow and the wrapping labels together, and means new panels are responsive by default rather than by discipline.

Step 5

Panel chrome: one header, everywhere

Give PanelHeader an actual .Title rule (44px bar, 13px/650 title, action slot, mode group) and move the components panel onto it. Restyle the tree — 26px rows, 12px labels, indent guides, category glyphs, accent-rail selection.

Step 6

Consolidate settings, then float and full

Merge App Setup into Project settings, put Project/Editor behind one gear. Then floating and full modes, with the Data/Schema/Permissions portals moved onto Full so there's one full-screen path instead of five ad-hoc ones.

Everything here is a proposal, not a decision — the mode system in particular is the part I'd most want you to poke at before it gets built. Steps 1 and 2 I'd do regardless.
