s44 stopped at step 3 and named **SBR-008 AC1**. s45 fixed the real cause (the health-verdict loop)
and drove it green. **This run found that step 3 was still blocked, by a second and unrelated

Full record: **[D52](../../DEFECTS-THE-SITE-BUILDER-FOUND.md#d52)**. It is fixed, in the generator,
and the byte-equality gate passes (`sb007Template.test.ts`, 62/62, `EXIT=0`).

🔴 **The lesson, because it is now three for three.** Every blocker in this phase has been a loop
whose two halves each look correct in isolation, and in each case the arm that would have shown it
was *"press the button and then read the record"*. s45 wrote that a fix graded on a healed fixture
is graded on the case it was not written for. **The same is true of a fix graded on the layer it
was written in**: s45's runtime fix was correct, complete, and still left the person unable to type
a heading.

## 4. 🔴 The instrument, and why it is not the product's own preview

The preview webview is **988×313** and `npm run cdp` has no resize verb. The documented route,
`Emulation.setDeviceMetricsOverride` on the same connection, **was tried and it does not work
here**: it moves `innerWidth`/`innerHeight` to 1440×900, and `Page.captureScreenshot` then returns
the **old 988×313 surface tiled** across the larger frame. The numbers all read correct and the
picture is an artefact. `captureBeyondViewport: true` returns a byte-identical file.

🔴 **A reading that fits is not one that excludes** — the metrics call reported exactly the success
it was asked for.

So every picture and every anonymous assertion in this run comes from a **plain headless Chrome on
its own CDP port with its own profile**, pointed at the same `:8574` the editor is serving. Scripts
in the session scratchpad: `drive.js` (persistent, signed-in), `anon.js` and `contact.js`
(one-shot, no session).

⚠️ **D51 does not bound these pictures, and the decisive reason is not the one first given.**
`sbr014-drive` does carry `noodl_modules/inter/`, `lucide-icons/` and `starter-imagery/` (the
wizard's create path places them; only `site-drive.ts` does not) — but that is the weaker argument.
🔴 **The site-builder template never asks for Inter at all**: it uses `var(--font-sans)` ×51 and
`var(--font-serif)` ×11, and `siteTheme.ts` overwrites both with explicit platform stacks
(`THEME_TOKEN_FIELDS`: `fontUi → --font-sans`, `fontDisplay → --font-serif`). ✅ Confirmed by this
run's own control pair: Studio's headings render **serif**, Night's render **Helvetica-like** —
`siteTheme.ts:126`. The type follows the **theme**, observed changing when the theme changed. See
the s46 note appended to D51.

### Traps this run paid for

- 🔴 **The viewer mints a fresh `input-<uuid>` on every re-render.** An id read before adding a
  section is stale by the time the section exists — address by DOM order instead.
- 🔴 **`scrollIntoView` does nothing here and neither does anything else** — see
  [D40](../../DEFECTS-THE-SITE-BUILDER-FOUND.md#d40). The run continued at a **1440×2600**
  viewport, which is an instrument workaround **a person does not have**.
- 🔴 **A substring text-matcher clicked `Published` when asked for `Publish`** — the status label,
  not the action button, and it reported a successful, reachable click on the wrong element. The
  same family as `onDrop` matching `onDropped`. Match button text **exactly**.
- 🔴 **`<title>` matches every text query and has zero area**, so it won a "smallest element"
  tie-break and then reported itself unreachable. Filter to rendered `body` elements.
- ✅ **Two absences in this run were only meaningful because a control fired first**: the wheel
  (a tall `file://` page scrolled) and the request capture (`Save page` produced its `PUT`).
  Without those, *"nothing scrolls"* and *"nothing sends"* were unmeasured, not measured.
