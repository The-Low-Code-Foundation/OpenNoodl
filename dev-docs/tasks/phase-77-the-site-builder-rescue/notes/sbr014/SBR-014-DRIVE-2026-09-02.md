## 3. 🔴 Why the drive stops at step 3 — SBR-008 AC1, at its worst

**A page created through the New page dialog has no title and no slug. Neither has the page after
the page editor saves it. The `Page` table never gains the columns at all.**

Driven twice, through two different input paths, so the result is not an artefact of the harness:

| page | how the fields were typed | title/slug in the record |
|---|---|---|
| `Home` / `home` | `cdp type` (`Input.insertText`) | 🔴 **absent** |
| `About Us` / `about` | native value setter + `input` event | 🔴 **absent** |

```
Page columns: ['objectId','createdAt','updatedAt','ACL','published','showInNav','navOrder']
```

The three columns that *are* written are exactly the three the create node carries as **literal
parameters** (`prop-published`, `prop-showInNav`, `prop-navOrder`). The two that are missing are
exactly the two that arrive **over a wire**:

```
closeResult-title → prop-title      (Pages/Admin, node 786de65e)
closeResult-slug  → prop-slug
closeAction-create → store
```

Then the **page editor's save** was driven on the same record: title `Home`, slug `home`,
`Save page`. The record's `updatedAt` **did not move** (`20:09:14.088Z`, unchanged) and no column
appeared. The screen showed neither an error nor a confirmation.

### Why this is SBR-008's AC1 and not a new defect

[SBR-008 §6.4](../../SBR-008-THE-DEPLOY-KEEPS-THE-PANELS-WIRES.md) already drove this symptom and
named the cause: on a fresh site a column exists only once something has written it, and the graph
that writes it is the graph whose `prop-` ports are missing, so `exportComponent` drops the wire as
unhealthy and *"the panel writes a page with no title, and the save reports success"*. §6.5 records
**AC1 as unmet** and says of the browser side: *"nothing yet fixes it."*

🔴 **What this drive adds is the severity.** In SBR-008's own drive `Title` **saved correctly**,
because that fixture's `Page` class already had a `title` column; only `seoDescription` was lost.
On a **wizard-fresh site there is no column for anything**, so the loss reaches the *primary*
fields, and it is a deadlock with no way out through the UI: the only way to create the column is
to write it, and the wire that would write it is the one being dropped.

⚠️ It also bears on **SBR-008 §5.5's open question**. That section proposed a *timing* account for
nameless rows and asked for a second page created late in a settled session. Two pages were created
here, two minutes apart in a settled session, and **both arrived nameless** — but on a fixture where
the column never existed, so this run is consistent with the circularity and does **not**
discriminate the timing hypothesis. §5.5's measurement still needs the `SBR-016 Arrive Drive`
fixture it names.

### The seam, and what is NOT yet measured

The runtime half of the fix **is present and shipped**: `recordWiredFieldPorts` (P77 SBR-008) is
called from `dbmodelcrudbase.ts:392` with `plug: 'input'`, and it is in the built viewer bundle
(`recordWiredFieldPorts` ×6, `recordWiredFieldNames` ×3; control `recordFieldPorts` ×5).

🔴 **So the surviving explanation is the editor-side export/health path dropping the wire before
the viewer ever sees it — and this run did NOT measure that.** SBR-008 §6.4 measured it on its own
fixture (four `prop-` wires unhealthy, exactly the columnless ones). Confirming it on *this* fixture
is the next session's cheapest first move.

**Population check** — the implicated code is at HEAD, not a peer's in-flight edit:
`record-ports.ts`, `dbmodelcrudbase.ts` and the export path are all clean in `git status`. The one
dirty template file (`site-builder.content.json`, +6 lines) adds `realtime`/`runOnChange-records`
to three `DbCollection2` nodes for the D46 live-preview work and does not touch the create wiring.

## 4. What the drive found on the way

### D49 — the claim screen shows both of its failure sentences before anything is attempted
On first render of `/admin/setup`, **both** *"This site cannot be claimed."* and *"That account
could not be created."* are visible — `display:flex`, `visibility:visible`, `opacity:1`, 708×19px,
and on top per `elementFromPoint`.

Cause, read off the artefact: each `Text` node ships `"visible": false`, but that parameter is
**inert** — a connection drives the port from a `Condition` node's `result`. Both `Condition` nodes
carry `runOnChange-condition: true` **and** a literal `condition: true`, so they evaluate at init and
push `true` into `visible` before any failure signal reaches their `eval` port.

Confirmed **at HEAD** (`git show HEAD:…site-builder.content.json`), where the two gates are named
`claimGate` and `signupGate` — so this is shipped, not a working-tree artefact.

🔴 **The consequence is worse than cosmetic:** because the sentences are always on, a *real* failure
is indistinguishable from the initial state. When the claim genuinely failed in §2.2, the screen
looked exactly as it had before the attempt.

This is the same family as the phase's `Run`-is-additive lesson: wiring `eval` does not stop a
`Condition` running on its own.

## 5. Traps this run paid for, for the next driver

- 🔴 **`grep` skipped every `.tsx` silently.** `grep -rn "ProjectCreationWizard" packages/…` returned
  hits *only* inside `index.bundle.js` and read as *"the wizard is stale-bundle-only"*. `grep -ra`
  found the eleven real source hits. **An absence measured without `-a` is unmeasured.**
- 🔴 **The first "the click did nothing" was a control reading zero.** `New project` was clicked,
  the wizard opened, and the probe looked at `#root`'s innerText and `.dialog-layer` — neither of
  which is where it renders. `[class*=ProjectCreationWizard-module__Modal]` showed it had been open
  the whole time. **Check the container before believing the absence.**
- 🔴 **`input[type="text"]` matched nothing** — the `type` seen in a probe was the DOM *property*
  default; there is no `type` attribute on these inputs. A client-side property read as a fact about
  the markup.
- ⚠️ The wizard's entry-mode cards are three nested elements; the clickable one is
  `button[class*=ModeCard-hit]`. Stamp it and click the stamp.
- ⚠️ Five of the eight backend surfaces (**Secrets** among them) are behind the card's `···`
  overflow (`[data-test=local-backend-more-<backendId>]`), and the menu renders **outside**
  `.popup-layer`.
- ⚠️ Page routes are the `Page` node's `urlPath` (`admin/setup`, `admin/pages`, `admin/signin`),
  not the component name. `/setup` silently falls through to the public catch-all at `{slug}`.
