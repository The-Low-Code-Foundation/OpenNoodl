## 2. The re-measurement changed six rows

Re-measuring is not a formality. Six rows came back different from how they were written, and two of
them would have sent a session at the wrong codebase.

### 🔴 P77 D6 — REFUTED as stated. `maxWidth` is not inert on `Text` for the reason given

D6 says *"`maxWidth` is **inert on `Text`** — authored, driven (`computed: none`), removed."*

Measured at HEAD, through the door a builder uses (`get_node_type("Text", ports:["maxWidth"])`):

```
"name": "maxWidth", "group": "Dimension Constraints",
"type": { "name": "number", "defaultUnit": "%", "units": ["%","px","vw","vh"] }
```

The port **is declared**, and the door knows it. `addDimensions`'s `useDimensionConstraints`
parameter defaults to **`true`** (`node-shared-port-definitions.ts:755`) and **no node in the
repository passes it at all**, so every visual node gets the constraint ports including `Text`.

🔴 **And the platform did not move under the row.** `node-shared-port-definitions.ts` was last
touched **2026-08-08**, three weeks before D6 was measured. The port was declared when D6 was
measured too. The row's *cause* is wrong, not stale.

⚠️ **The symptom is unexplained and the row stays open as a disproved cause.** Something removed the
property; it was not the port being absent. The two candidates worth an hour: the `%` coercion of
§2's D8 row (a bare `maxWidth: 240` becomes `240%`, which is not `none` but is not what was wanted
either), and `Text`'s own contextual port filtering, which the catalogue announces —
*"explicit width/height ports appear only in the matching size mode."*

### 🔴 P77 D2 — REAL, but the cause is wrong for the third time, and the fix is much smaller

D2 says step recording *"is wired to the workflow engine, and a cloud function's graph is run by a
different executor that never calls it."*

**The cloud function path does call it.** `WorkflowRunner.ts:261` is inside the **`Log` node
handler**:

```ts
if (execLogger) {
  const stepId = execLogger.startNode({
    nodeId: (entry && entry.nodeId) || 'log',
    nodeType: 'net.noodl.Log',      // ← hardcoded
    ...
  });
  execLogger.completeNode(stepId, true);
}
```

So a cloud function writes **one step per author `Log` line**, and nothing else. The site-builder
template contains **zero** `net.noodl.Log` nodes
(`site-builder.content.json`, 190,781 bytes, `grep -c net.noodl.Log` → **0**), which is the whole
explanation of the drive's *"3 executions and 0 steps"*.

🔴 **The correct sentence is: `execution_steps` records what the author chose to log, never what the
graph actually ran.** That is a better defect than the one recorded — the recorder is already
reachable from the cloud path, so the fix is to call it where the graph *steps*, not to wire up a
second executor. **D2's own file already warns that its first two readings were wrong. This is the
third.** Whatever is going on with this row, the pattern is that it gets diagnosed from the caller
list without reading the caller.

### 🔴 P77 D4 — RECLASSIFIED: template, not product. And it contradicts P78 D4

P77 D4: *"a refused query and an empty collection are the same screen."*
P78 D4: **✅ ANSWERED on the drive — "yes, `failure` fires."** Measured on one backend, two arms:
member `200` + row drawn; pending person `403` + `failure` fired + `query-records/query-failed` in
the console.

Confirmed at HEAD through the door — `DbCollection2` carries both:

| port | type | group |
|---|---|---|
| `failure` | **signal** | Events |
| `error` | string | Error |

🔴 **So the product gives an author the means and the site builder never wired it.** P77 D4 is
**template work**, it is not Richard's call, and it belongs to SBR-006/SBR-010 as an ordinary
acceptance criterion. Left as written it would have opened a platform task for a wire.

⚠️ **This also invalidates a claim carried in working memory across many sessions** — *"a refused
query publishes `[]` like empty"*. It does not. That note has been corrected.

### 🔴 P77 D8 is P76 F15. The same defect, recorded twice, unowned in both

- **P76 F15** (s6): *"a bare number on a dimension port being read as a **percentage**"*
- **P77 D8** (s9): *"a bare number in a dimension port means **percent** (`width: 240` → `240%`)"*

**REAL at HEAD**, `react-component-node.ts:1925`:

```ts
if (typeof value !== 'object' && type.defaultUnit) {
  value = { value, unit: type.defaultUnit };   // 240 → { 240, '%' }
}
```

Two phases found it independently, neither gave it an owner, and neither knew about the other. **It
is one row and it needs one task.**

### 🔴 P78 D11 — REAL, numbers exact, and WIDER than recorded

The three failing ratios reproduce exactly (`--primary-foreground` on `--primary`, AA 4.5 floor):

| preset | ratio | |
|---|---|---|
| modern | **3.68** | 🔴 the wizard's default |
| playful | **4.23** | 🔴 |
| soft | **4.47** | 🔴 |
| minimal | 17.72 | ✅ |
| enterprise | 17.85 | ✅ |

🔴 **But `ModernPreset.ts` ships `tokens: {}`** — *"Modern IS the defaults"*. So `3.68` is not
Modern's ratio, it is **`DefaultTokens.ts`'s**: `--primary: #3b82f6` on `--primary-foreground:
#ffffff`. Every project inherits it, including every project whose author never opened the preset
picker.

**The row is not "3 of 5 presets fail". It is "the product's default primary button fails, and two
presets fail as well."** That is a different, larger claim, and it is why this ranks first in §4.

### ⚠️ P76 F16 — REAL, and sharper than recorded: it is not only an export problem

F16 was recorded as *"a `Page` node's **`title` port is dead after export**"*. At HEAD, through the
door:

```
"notFound": ["title"]
"runtimeBehavior": "`title` and `urlPath` are registered per instance
                    by the editor connection"
```

🔴 **The port does not exist unless an editor is attached.** So it is not that the title dies at
export — it is that **an agent authoring headlessly through the MCP door cannot set a page title at
all**, and the door reports it as an unknown port rather than as a limitation. On a template whose
product is a *website*, that is the SEO surface.

### 🔴 The collision this created, and the ruling

Both halves were fixed **the same day by two sessions that could not see each other**: this sweep
disambiguated the duplicate by lettering it `D10a`/`D10b`, while phase 78's owner renumbered the
second half to `D17`. One problem, two fixes, and afterwards the same row had two names.

**Ruled 2026-08-29: the register's numbering wins. `D10a` → `D10`, `D10b` → `D17`**, applied here
and across phase 80.

The reason, so the next collision resolves the same way: **the register mints `D` ids; phase 80
mints `DEF` ids.** A file should be renamed to match the file that issues its identifiers, never
the other way round. `D10b` was also the worse name on its own terms — the letter implies a part
of `D10`, and it is an unrelated defect.

⚠️ **Phase 78's file still carries the equivalence note** written while phase 80 said `D10a`. It
is now describing a state that no longer exists and can be simplified — their lane.

## 6. The rule this sweep exists to enforce

🔴 **A template-scoped test does not close a row.** SBR-015 is the worked example: the rule *a cloud
function's `Failure` must reach a Response* ships as a spec in the template's own suite. It protects
**one template and no user** — `validate.ts` still ships the hole, which is why P77 D1 is open at the
top of §4 rather than closed.

**Checked, and no other row has been quietly closed the same way.** The three closed-by-fix rows
(P78 D7, D14, D16) each changed the *artefact*, and each says in its own text which half is the
template's and which is the product's. D14 is the one to watch: its template half is fixed and its
product half — `Run` is additive, third appearance — is unowned and is in §4 rank 4's neighbourhood.

⚠️ **Every disproved row was kept**: P78 D4, D6, D8, D17, and now P77 D6. Five of them, and D4 is
the most valuable row in any of the three files because it **reversed** a belief that had been
relayed across sessions and was still in working memory this morning.
