# Phase 27: Visual Backend Authoring (Revival Track L)

**Phase:** 27
**Track:** L — make the backend something you can see, edit and debug without writing JSON
**Source:** Scoping session 2026-07-27, following a live end-to-end test of phase 19's workflow engine (see the findings register in [PROGRESS.md](./PROGRESS.md)).
**Status:** 📋 Specced, not started — 7 tasks.
**Starts:** Anytime. WFA-001 and WFA-002 are independent of everything else and independently valuable.

## Why this phase exists

Phase 19 built a genuinely good backend. A live test on 2026-07-27 drove the whole exit criterion for
real — a webhook and a cron both firing one workflow that wrote records, branched on a real value,
retried a failing charge three times with backoff, routed the failure to a handler that received
`previous.error.statusCode`, merged the paths and read the database back — and every part of it
worked, survived a restart, and recorded per-step input, output, status and duration.

None of it is reachable from the editor.

That is not one omission. It is four independent ones, and only the last was a decision:

1. **The Components panel is configured to hide the cloud sheet.** `hideSheets: ['__cloud__']`
   ([`router.setup.ts:79`](../../../packages/noodl-editor/src/editor/src/router.setup.ts#L79)) filters
   cloud components out of both the tree and the sheet dropdown, so they are invisible even under
   "All".
2. **The panel that was supposed to show it was deleted.** `CloudFunctionsPanel.tsx` was 72 lines — a
   `ComponentsPanel` locked to `lockCurrentSheetName: '__cloud__'`. WF-007 removed it (`1a9557e0`)
   alongside the genuinely-dead Parse *management* UI. It was not Parse management; it was the cloud
   function authoring door.
3. **All three "create component" menus hardcode `forRuntimeType: 'browser'`**
   ([`ComponentsPanelReact.tsx:202`](../../../packages/noodl-editor/src/editor/src/views/panels/ComponentsPanelNew/ComponentsPanelReact.tsx#L202),
   [`FolderItem.tsx:176`](../../../packages/noodl-editor/src/editor/src/views/panels/ComponentsPanelNew/components/FolderItem.tsx#L176),
   [`ComponentItem.tsx:178`](../../../packages/noodl-editor/src/editor/src/views/panels/ComponentsPanelNew/components/ComponentItem.tsx#L178)),
   so the `Cloud Function Component` template that still exists in
   [`ComponentTemplates.ts:135`](../../../packages/noodl-editor/src/editor/src/views/panels/ComponentsPanelNew/ComponentTemplates.ts#L135)
   is never offered anywhere.
4. **WF-001 workflows were built API-first and have no canvas at all.** That one *was* a decision, and
   WF-002's own notes record it as an open residual: "there is no editor authoring UI for WF-001
   workflows anyway, so 'appears in the node picker' has no referent."

Items 1–3 are a **regression against old Noodl**, restorable in about a week. Everything downstream of
the canvas is intact and untouched: the template, the cloud node types, `CloudFunctionAdapter`, the
drag-a-function-onto-a-browser-graph caller, the `componentKind` detection that still labels these
"Cloud function" with their own icon, and the trail's `if (name === '#__cloud__') return null`.

## The shape of the answer

This phase is not "restore old Noodl's Cloud Functions panel." Three findings from the test change
what is worth building.

### The step DAG is already node-shaped

WF-002 deliberately took its port names from the shipped client `Condition` node rather than the
spec's camelCase — `ontrue`/`onfalse`/`result`/`isfalse`. A step has one input, a `next` output,
named `routes.*` outputs and an `onError` output. That is a graph wearing a JSON costume, and it maps
1:1 onto the canvas idiom NodeGX already draws.

The blocker WF-002 cited — step kinds structurally cannot enter `node-catalog.json`, because that
file is generated by *running* the two node registers and `catalog:check` deletes anything
hand-written — does not block a canvas. The backend already **serves** the equivalent at
`GET /admin/workflow-step-kinds`: a versioned table with params, types, routes and output shape per
kind. That is a node registry over HTTP, and it is *better* than the static catalog for this purpose
because it cannot drift from the backend you are actually targeting.

### The run inspector already exists and already speaks step ids

WF-006 built `ExecutionOverlay` — status badges positioned at node bounds, a popup showing a step's
input/output/error/timing, and a timeline scrubber that steps through an execution. It keys on
`step.nodeId → getNodeBounds(nodeId)`
([`ExecutionOverlay.tsx:38,77`](../../../packages/noodl-editor/src/editor/src/views/CanvasOverlays/ExecutionOverlay/ExecutionOverlay.tsx#L38)).

The workflow engine writes the **workflow's own step ids** into that field. A real run recorded
`nodeId: "save"`, `"decide"`, `"charge"`, `"logfail"` with `nodeType: "function:saveOrder"`,
`"branch"`, `"retry:chargeCard"`, `"merge"`. So a workflow canvas that uses step ids as node ids gets
the existing overlay for free.

This is why **WFA-002 comes before the canvas**. The distrust this phase exists to answer does not
bite when an AI lays out a graph; it bites at 3am when a workflow misbehaves and the only artefact is
JSON nobody wrote. An authoring canvas you cannot watch execute is a JSON editor with rounded
corners. A run inspector over an AI-authored workflow gives ownership immediately, and almost all of
it is already built and switched off.

### The security decision pre-paid for the editor

Conditions are a closed declarative operator set specifically because an `eval`'d string inside a
persisted, deployable, agent-authored artifact is an RCE surface behind an admin credential. That
constraint is exactly what makes a condition renderable as *left value / operator / right value*
instead of demanding a code editor. What looks like a limitation is what makes it visually editable.

## Three tiers, each visual, each with a deliberate exit

The phase does not try to make one graph language do everything. It builds a ladder where you descend
only when you choose to:

| Tier | Surface | What it is for |
|---|---|---|
| **Orchestration** | The workflow canvas (WFA-004) | Trigger → steps → routes. Sparse, control flow only. The n8n layer. |
| **Computation** | A cloud function graph (WFA-001) | The full Noodl node vocabulary, on the existing canvas, running on the backend. |
| **Code** | The JS `Function` node inside a cloud function | The existing escape hatch, unchanged. |

Nothing is throttled. WF-002 already designed the orchestration layer to punt real work downwards
("arithmetic inside a condition is not expressible — compute it in a function"), so expressiveness
lives one rung down where the whole node library is, and one rung further down in JavaScript. The
descent is visual at every rung.

**WFA-006 makes the ladder feel like one language.** A `call-function` step is a component instance:
double-click it and descend into that function's graph, with the existing `NodeGraphComponentTrail`
showing `Order Pipeline › saveOrder`. Noodl users already know that gesture. The two execution models
stay correctly separate underneath — WF-001-SEMANTICS is right that they are incompatible, and merging
them would mean reimplementing durable execution inside the Noodl runtime — but the seam reads as a
zoom level rather than a context switch.

## The decisions this phase starts from

Taken in the 2026-07-27 scoping session. Settled unless a task's assessment step contradicts them, in
which case the assessment wins and the deviation is recorded.

**Reuse, or don't build it.** Every visual surface in this phase is the *existing* canvas, the
*existing* execution overlay, the *existing* property editor pattern, the *existing* component trail,
and the *existing* AIX-003 diff review. This codebase's failure mode is half-wired UI, and a bespoke
second canvas is exactly how that happens. If a piece turns out to need a new surface rather than a new
node type, that is evidence against building it — escalate rather than fork.

**Debugger before editor.** WFA-002 ships before WFA-004 and does not depend on it. If the phase
stopped after tier 1, users would have visual cloud functions and a step-by-step run inspector over
AI-authored workflows — already most of the ownership this phase is about.

**The step-kind registry is served, not generated.** The canvas's palette and the property editor's
field types come from `GET /admin/workflow-step-kinds` on the backend the workflow will actually run
on. No entry is added to `node-catalog.json`; WF-002's argument for why that is structurally
impossible still stands, and the served table is the better artefact anyway. This does mean the
palette is **empty when no backend is running** — WFA-004 must handle that state honestly rather than
falling back to a stale bundled copy that can lie about what the backend supports.

**The two execution models stay separate.** Cloud function graphs are dataflow with signals, frames
and per-instance state. Workflow steps run once, in DAG order, only if an edge reached them. WF-001's
semantics doc argued this and it was re-examined in scoping; merging them would mean reimplementing
durable execution inside the Noodl runtime. The UI hides the seam (WFA-006); the runtimes do not
pretend it is not there.

**AI proposes; the canvas is where you accept.** WFA-007 adds no new AI capability — MCP can already
author workflows today. What it adds is that the output arrives as a reviewable diff on a canvas
instead of JSON accepted blind. The AI story and the visual story are the same story: the canvas is
what makes AI output trustworthy.

## Sequencing notes

- **WFA-001 is worth doing whether or not the rest of the phase is agreed.** It is a regression fix.
  Today a user cannot author a cloud function at all, and everything phases 19 and 22 built is
  unreachable without hand-editing JSON in a data directory.
- **WFA-003 is a prerequisite for the canvas, not a follow-up to it.** A step's input is
  `{...runPayload, ...params, previous}` with static literals only
  ([`WorkflowEngine.ts:397`](../../../packages/nodegx-backend/src/workflow/WorkflowEngine.ts#L397)).
  On a canvas the first thing every user will try is dragging a wire from `save.orderId` into
  `charge.amount`, and today there is nothing to receive it. Building the canvas first produces an
  editor that cannot express the obvious.
- **WFA-005 carries two shipped defects** found by the live test (F7 and F8 in the findings register):
  a webhook secret sent as `Authorization: Bearer` can never authenticate, and a schedule trigger
  silently discards a `payload` key it accepts with a 201. Both are in the trigger surface this task
  rebuilds, and the second blocks the phase-19 exit criterion's "webhook **and** on a schedule".
- **Tiers are stopping points.** Tier 1 alone closes a regression and lights up debugging. Tier 2
  makes workflows expressible. Tier 3 is the visual authoring story. Tier 4 is the part most worth
  challenging before it is built.

## What this phase deliberately does not do

- **No second canvas implementation.** See the reuse decision above.
- **No step kinds in `node-catalog.json`.** WF-002 §6's argument stands.
- **No new step kinds.** Debounce stays deferred for the reason WF-002 gave (it needs cross-run state
  the in-memory durability policy does not have). `for-each` keeps iterating a function rather than a
  sub-graph, so no nested canvases are required.
- **No durable/resumable workflow runs.** WF-001's headline residual — runs are in-memory, no
  cross-restart resume — is real and is *not* in this phase. A canvas over a non-resumable engine is
  still worth having; conflating the two would double the phase.
- **No visual editor for triggers' `db-change` filters beyond what the existing panel offers.**
  WFA-005 puts triggers on the canvas; it does not redesign filter authoring.
- **No AI capability that does not already exist.** WFA-007 is a review surface, not a new agent.

## Verification posture

Two rules, both learned the expensive way in phases 19 and 23:

1. **Every task ends with a live pass in the running editor**, driven by the `run-editor` skill, with
   screenshots. The four cuts this phase repairs were all invisible to a green test suite — the editor
   suite passes today with cloud function authoring completely unreachable. A test that does not open
   the app cannot see this class of defect.
2. **A test reads the live contract wherever one exists.** WFA-004's palette must be asserted against
   a running backend's `GET /admin/workflow-step-kinds`, in the pattern WF-003's `deploy-assets.test.ts`
   established, rather than against a hand-written list of the nine kinds.
