## Objective

Draw a WF-001 workflow as a node graph on the existing canvas, and let someone author and edit one
there — steps as nodes, `next`/`routes.*`/`onError` as connections, params in the property editor —
so that a workflow is something you look at rather than something you are told about.

## Background

### It is already a graph

WF-002 chose its vocabulary to match the canvas. A step has one incoming edge and up to three kinds of
outgoing edge:

| Edge | Taken when | Draws as |
|---|---|---|
| `next` | the step succeeds, whatever it decided | the default output |
| `routes.<name>` | the step succeeds and selects that route | a named output port |
| `onError` | the step fails | an error output port |

`branch`'s routes are literally `ontrue` / `onfalse` and its output is `{result, isfalse}` — taken
from the shipped client `Condition` node on purpose, because WF-002 preferred the real node's names
over the spec's. `switch` has dynamic route names, one per case label, plus `default`. That is the
node-with-ports idiom NodeGX already draws.

### The palette is served, not generated

`GET /admin/workflow-step-kinds` returns a versioned table (F20). Per kind:

```jsonc
{
  "kind": "retry",
  "displayName": "Retry",
  "category": "Workflow",
  "summary": "…",
  "whenToUse": "…",
  "invokesFunction": true,
  "params": [
    { "name": "maxAttempts", "type": "number", "required": false, "description": "…" },
    { "name": "retryOnStatus", "type": "array", "required": false, "description": "…" }
  ],
  "routes": [{ "name": "…", "description": "…", "dynamic": true }],
  "output": "…",
  "clientEquivalent": "…"
}
```

Param `type` is one of `string | number | boolean | enum | array | object | condition | path | any` —
enough to pick a control without hardcoding the nine kinds. WF-002 argued at length why these cannot
enter `node-catalog.json` (it is generated by running the node registers; `catalog:check` deletes
hand-written entries), and that argument stands. The served table is the registry for this canvas, and
it is the better artefact: it comes from the backend the workflow will actually run on, so it cannot
describe a kind that backend cannot execute.

### The overlay is waiting

`ExecutionOverlay` keys on `step.nodeId → getNodeBounds(nodeId)` and the engine writes the workflow's
own step ids into `nodeId` (F15). If canvas node ids **are** step ids, WFA-002's inspector works over
this canvas with no changes to the overlay. Do not invent a separate id space and a mapping table.

## Desired State

### 1. The architectural decision, taken and recorded first

**Is a workflow a component with a third `RuntimeType`, or its own document type?** This is the
decision that is expensive to get wrong, and it must be taken in an assessment step with the reasoning
written down before any canvas code.

The pull towards a third runtime type: `RuntimeType` is a two-value enum with an array beside it,
`NodeGraphContext` already flips an active graph on it, and the canvas already renders "a graph that
is not the browser graph".

The pull away from it: a workflow is **not a component**. It has no ports, cannot be instantiated,
has no parent graph, and — critically — **does not live in the project**. Workflow definitions are
stored in the backend's data directory (`<dataDir>/workflow-defs/<id>.workflow-def.json`), not in
project files. They do not travel through version control, do not appear in a project export, and are
not deployed with the app. Modelling them as components will imply all four of those things falsely.

Whichever is chosen, the record must answer: where do workflows appear in the UI, what happens to them
on `git clone`, and what happens on deploy. The last one is a real interaction with phase 26 — a
workflow that is not in the artifact does not get deployed with the app — and this task does not have
to *solve* it, but it must not pretend it does not exist.

### 2. Steps render as nodes

- **Node id = step id.** Non-negotiable; it is what makes WFA-002's overlay work here.
- Node label is the step's `name` if set, else its `id`. Node subtitle is the kind's `displayName`.
- `call-function` and `retry` show the function they invoke — that is the single most useful thing on
  the card.
- Ports: one input; `next`; one output per entry in the kind's `routes`; `onError`. `switch`'s
  dynamic case labels come from its `cases` param, in the pattern the existing dynamic-port
  mechanisms already use.
- Colour by category from the served spec, through `CanvasTheme` tokens. UIX-005 made the canvas
  token-driven and deleted the hex palette; do not reintroduce one. `onError` uses the danger token —
  which under phase 23's law is the *only* legitimate use of red.

### 3. Edges are connections

- `next` is the plain edge. `routes.*` edges carry their route name as a visible label — an unlabelled
  branch is unreadable, and this is the one place a workflow graph differs from a browser graph in a
  way the user must see.
- `onError` edges are visually distinct (danger token, and a different line treatment so it survives
  colourblindness and greyscale screenshots).
- Creating a connection writes `next` / `routes.<name>` / `onError` on the source step.
- **The acyclicity check is enforced at author time**, not only on save. The engine validates and folds
  routes into its acyclicity check already; a canvas that lets you draw a cycle and then refuses to
  save it is worse than one that will not let you draw it.

### 4. Params in the property editor

Selecting a step shows its params, with controls chosen from the served `type`:

- `enum` → dropdown from the spec's values.
- `condition` → the three-part editor the closed operator set makes possible: left value, operator,
  right value, where each value is literal / `$path` / `$literal`. **This is the control that decides
  whether the canvas is genuinely usable**; a JSON textarea here fails the task.
- `path` and WFA-003's `$path` params → a picker over reachable predecessors and their outputs, with
  free text as the fallback. A dangling reference is flagged in the editor, matching WFA-003's
  write-time 400.
- Everything else → the obvious control, with the spec's `description` as help text and `whenToUse` on
  the kind itself.

### 5. Layout

MCP- and AI-authored workflows have no coordinates.

- Auto-layout (DAG layering) on first open of a workflow with no stored positions.
- Positions persist thereafter. **Where** they persist is a decision this task takes: alongside the
  definition on the backend (travels with the workflow, pollutes a deployable artifact with editor
  state) or in editor-local storage keyed by workflow id (clean artifact, lost on another machine).
  Say which and why.
- Adding steps to an existing workflow — by hand or by WFA-007 — must place them without disturbing
  the user's arrangement of everything else.

### 6. No backend, no lies

The palette comes from a running backend. With none running, the canvas must say "start a backend to
author workflows" and offer the way to do it. It must **not** fall back to a bundled copy of the step
kinds: a stale copy that offers a kind the target backend cannot execute is precisely the drift the
served registry exists to prevent.

### 7. Run it from the canvas

A Run affordance that posts to `POST /admin/workflow-defs/:id/run` and, when the execution returns,
pins it to this canvas through WFA-002's existing `execution:pinToCanvas` path — so authoring and
watching are one gesture. This is where the phase pays off, and it should be demonstrated in the live
pass as one continuous screen recording or screenshot sequence.

## Implementation Steps

1. **Assessment**, ending in a written decision on §1 plus a walk through the canvas code identifying
   exactly which extension points are used. If that walk concludes a new surface is required rather
   than a new node type, **stop and escalate** — that is the README's reuse-or-escalate rule, and it
   is a legitimate outcome.
2. **Read-only render first.** Load a real workflow from a running backend and draw it. No editing.
   This is the checkpoint that proves the reuse thesis, and it should be reachable in the first week.
   Screenshot the phase-19 test workflow (8 steps, a branch, a retry, an error route and a merge).
3. **Overlay over it** — pin an execution of that workflow and confirm badges land on the right nodes
   with no overlay changes. If the overlay needs changes, that is a finding worth recording.
4. **Palette + creation** from the served spec.
5. **Connections**, including route labels and author-time acyclicity.
6. **Property editor**, condition control first — it is the riskiest control and the one that decides
   usability.
7. **Layout** and its persistence decision.
8. **Run + pin from the canvas.**
9. **Docs**: correct `WORKFLOW-NODES.md`'s "Author them: the Backend Services panel" (F10) to describe
   what now exists.
10. **Live pass** on a workflow with all nine kinds represented, both themes, screenshotted.

## Success Criteria

- [ ] The §1 decision is recorded with its reasoning before canvas code was written.
- [ ] An existing workflow authored over the admin API renders as a graph, with routes labelled and
      the error path visually distinct.
- [ ] Canvas node ids are step ids, and WFA-002's overlay works over this canvas **without
      modification** — or the required modifications are recorded as a finding.
- [ ] A workflow can be created from scratch on the canvas and runs on the backend.
- [ ] A condition is edited without touching JSON.
- [ ] A `$path` param is set from a picker over reachable predecessors, and a dangling one is flagged.
- [ ] Drawing a cycle is prevented at author time.
- [ ] A workflow with no stored positions lays out readably on first open; a hand-arranged one is not
      disturbed by adding a step.
- [ ] With no backend running, the canvas explains that rather than showing an empty palette.
- [ ] Run-and-pin works as one gesture from the canvas.
- [ ] Rendered in both themes with tokens only; a hex-literal check passes for the new files.
- [ ] `docs/runtime/WORKFLOW-NODES.md` no longer describes a surface that does not exist.

## Out of Scope

- **New step kinds.** Nine exist; this task draws them.
- **`for-each` sub-graphs.** It iterates a function by design. It draws as one node; whether that
  reads clearly is an open question the live pass should answer, not a licence to build nesting.
- **Triggers on the canvas.** WFA-005.
- **Descending into a function.** WFA-006.
- **AI authoring.** WFA-007.
- **Deploying workflows with an app.** Named in §1 as a real interaction with phase 26; not solved
  here.

## Traps

- **The canvas is Canvas2D and the node view is a stateless painter** (PLAT-001 wave 4). New node
  types are painted, not composed from DOM. Read `nodeAttachment` and the ≤800-line rule before
  adding to those files.
- **`getNodeBounds` resolves against the currently open graph.** WFA-002 made the mismatch case
  honest; this task must make it correct.
- **UIX-005 deleted `NodeGraphColors.ts` and made the canvas repaint on `nodegx:themechanged`.** A new
  node type that caches a colour at construction will be wrong after a theme toggle.
- **`switch` route names are dynamic and come from a param**, so ports change as `cases` is edited.
  The existing dynamic-port machinery has a documented trap: a type set at registration time is the
  one that sticks (see `simplejavascript.ts`'s `intype-` comment).
- **The editor's spec suite is Jasmine, not Jest.** New editor specs follow the editor's conventions.
- **`--target=editor` in CDP silently attaches to the preview window once a project is open.** Use
  `--target=dashboard`, launch detached, never `cdp reload`.
- **A worktree cannot drive the editor** (`lerna exec` resolves to the main checkout). The live pass
  runs from the primary checkout.
- **Workflow definitions are validated on load and an invalid file refuses to start the backend.** A
  canvas that can write a definition the validator rejects can stop a backend from booting. Validate
  before writing, and prove it with a test that tries.
