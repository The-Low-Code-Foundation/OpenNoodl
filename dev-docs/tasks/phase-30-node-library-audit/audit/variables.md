## Shared helper — audit it once

All four nodes are `VariableBase.createDefinition(...)` over
[`variablebase.ts`](../../../../packages/noodl-runtime/src/nodes/std-library/variables/variablebase.ts).
Each supplies only `name`, `type`, `startValue` and `cast`. **Every defect below except the cast
behaviour is one defect in `variablebase.ts`, not four** — see the batching warning in NDA-012.

| Helper defect | Citation |
|---|---|
| `changed` never fires when a Variable is set to its own `startValue`; `initialize` seeds `currentValue` so a real set is indistinguishable from the seed | [`variablebase.ts:47-50,96-106`](../../../../packages/noodl-runtime/src/nodes/std-library/variables/variablebase.ts#L96-L106) |
| `cast` runs on every store and is the only null-handling in the node — the base offers no empty-value policy at all | [`variablebase.ts:96-97`](../../../../packages/noodl-runtime/src/nodes/std-library/variables/variablebase.ts#L96-L97) |
| No Failure output and no way to express one; the `Set` path cannot report a rejected value | `variablebase.ts:78-94` |
| `latestValue` initialises to `0` regardless of type, so a String variable whose `Set` fires before any `value` arrives stores `"0"` | [`variablebase.ts:49`](../../../../packages/noodl-runtime/src/nodes/std-library/variables/variablebase.ts#L49) |

That last one was **not** in the first pass. It is a fifth Variables defect, found by running this
protocol — which is the argument for NDA-012 in miniature.
