# TALK-007 — What should a cloud function be able to do?

**Created:** 2026-08-05. **Status:** open working doc — Richard adds ideas, I annotate them with
cost and a verdict, then [TALK-001](TALK-001-THE-CLOUD-WORKFLOW-AUDIT.md) reopens to decide what
gets built.

**Why this exists.** TALK-001 audited the *workflow step* catalog and accepted "workflows
orchestrate, **cloud functions compute**" as the answer to every gap — without ever auditing what a
cloud function can compute *with*. That was the hole in the conversation. This doc closes it.

## How to use this doc

Add anything you want to §5 — one line each, no format required, half-formed is fine. I'll come
back and fill in the cost, the realism verdict, and what it would break. Then we reopen TALK-001,
decide the list, and the survivors become CWF tasks like the rest of the track.

Verdict key I'll use: **Free** (already exists, needs a door) · **Cheap** (a move + a registration
line) · **Real** (needs designing, days) · **Deep** (touches the runtime contract) · **No** (with
a reason).

## 2. The thing you asked me to check — and the answer is not the one you expected

> *"Pretty sure that's wrong, they're not in my node picker when I'm in the cloud function canvas."*

**They are.** Driven live: created a cloud function component, confirmed the canvas resolves
`runtimeType: "cloud"`, opened the real picker, and read it back. Under **Read & Write Data** it
offers, verbatim: *Subscribe to Store, Optimistic Update, State History, Undo / Redo, State
Snapshot* (App State, 7 with the two other Global Store nodes) and *Action Dispatcher, Action
Handler* (Agent Actions, 2). **Component Children** is offered under Component Utilities.
Screenshot: `scratchpad/cloud-picker-appstate.png`.

**Why it's easy to be sure otherwise:** they are two levels down. The picker opens on *General
Utils → Logic → String Manipulation*, and the App State group sits at the bottom of a 32-node
category you have to select first. Nothing about the top of that picker suggests they're in there.

The mechanism is uninteresting and the consequence isn't: the agentic-UI batch (AIX-005) was
registered in the **shared** runtime rather than the viewer, so all fourteen of those nodes went
into the cloud registry as a side effect. Nobody chose it.

**So the decision stands, unchanged by the correction:** Global Store ×3, Optimistic Update, State
History, Undo/Redo, State Snapshot, Action Dispatcher, Action Handler, Component Children — 9 nodes
offered to a server-side function where they range from useless to actively misleading. The
Streaming six I'd keep (calling an upstream streaming API server-side is exactly
[CWF-007](CWF-007-STREAMING-RESPONSES.md)'s case). *Your call — it's in the list below.*

## 3. The gaps, in three piles

### Pile A — absent for no technical reason (**Cheap**)

Every node here imports **only `@noodl/runtime`** — no React, no DOM. They live in the viewer
package by history, not dependency ([collectionnode2.ts:3-5](../../../packages/noodl-viewer-react/src/nodes/std-library/data/collectionnode2.ts#L3-L5),
same for filter/map/variable/switch/remapper/valuechanged). Moving them is a file move plus a
registration line, then regenerate the snapshot.

- **The entire array family** — Array, New Array, Insert, Remove, Clear, Filter Array, Map Array,
  Static Data. **A cloud function cannot build, filter or reshape a list with nodes.**
- **Variable / Set Variable** — no scratch state between parts of a function.
- **Switch** (only two-way Condition today), **Number Remapper**, **Value Changed**.
- **HTTP Request** — already [CWF-003](CWF-003-HTTP-IN-THE-CLOUD-RUNTIME.md).

**Correction to something I said earlier:** cloud functions *can* iterate. **Run Tasks** is
registered and is the server-shaped For Each — `items` in, a component template per item,
concurrency, stop-on-failure ([runtasks.ts:151-250](../../../packages/noodl-runtime/src/nodes/std-library/runtasks.ts#L151-L250)).
For Each itself imports React and is genuinely browser-shaped. The gap is *producing and reshaping*
arrays, not looping over them.

### Pile B — present but browser-shaped

The nine in §2. Options: un-register for cloud (check first whether any existing function uses
one), or keep and document. Un-registering is a one-line-per-node change plus a snapshot
regenerate.

### Pile C — your auth ask, which is half-built already

You wrote: *"all the data nodes should be available in cloud functions, create user etc but also
querying records and even grabbing a JWT to authenticate the user in the backend… We also need a
way to mark a cloud function as public or only available if the user is authenticated."*

Sorting that against the code:

- **Querying records: already there.** Record, Query Records, Create/Update/Delete Record, Filter
  Records, relations, Cloud File, Config — 11 nodes, in the picker today (§1).
- **Public vs authenticated per function: the backend already does this.** Every call to
  `POST /functions/:name` resolves a rule from `security.config.functions[name].call`, accepting
  `public | authenticated | nobody | role:<name>`, with a `runAs` alongside it
  ([HttpServer.ts:1500-1512](../../../packages/nodegx-backend/src/server/HttpServer.ts#L1500-L1512),
  [security/model.ts:58-99](../../../packages/nodegx-backend/src/security/model.ts#L58-L99)).
  There is an admin API (`AdminSecurityRoutes`) and **no editor UI whatsoever** — I searched the
  panels for it and found nothing. **Free**: this is CWF-001's shape again — a built mechanism with
  no door. A per-function dropdown in the Cloud Functions panel is most of the work.
- **Create user / verify a token server-side: genuinely absent.** The cloud runtime has User and
  Set User Properties; Sign Up, Log In, Verify Email, Reset Password, Sign In With, Magic Link are
  all browser-only — and unlike Pile A that's *defensible*, because they're session-shaped (they
  set a client session). A server-side equivalent (Create User, Verify Token, Get Caller) needs
  designing, not porting. **Real.**
