# Node Catalog Schema

**Artifact:** `packages/noodl-types/src/node-catalog.json`
**Types:** `packages/noodl-types/src/node-catalog.d.ts`
**Generator:** `scripts/node-catalog/generate.js` (`npm run catalog:generate`, CI gate: `npm run catalog:check`)
**Catalog format version:** 1.0.0

The catalog is the machine-readable vocabulary of every node type the NodeGX
runtimes register: canonical type strings, ports, value types, defaults, enums,
and — critically — an explicit model of which nodes have ports that *cannot*
be known statically. It is generated by loading the real node registries
headlessly (never by parsing node source files), so it cannot drift from what
the runtime actually accepts. A CI check regenerates it on every PR and fails
if the committed artifact is stale.

This document is written for a reader — human or AI — with **no other
context**. If you are authoring or validating project files, this file plus
the catalog and the v2 project schemas are intended to be sufficient.

## How the catalog relates to project files

A node in a project/component file looks like:

```json
{
  "id": "a1b2c3…",
  "type": "Group",
  "parameters": { "flexDirection": "row" },
  "children": [ … ]
}
```

and a connection looks like:

```json
{ "fromId": "a1b2c3…", "fromProperty": "screenPosition.x", "toId": "…", "toProperty": "value" }
```

The catalog answers, for each `type`:

- Is this a real node type? (`nodes[].typeName` — exact, case-sensitive match)
- What may appear as a key in `parameters`? (input port names)
- What may appear as `fromProperty` (an **output** port of the `fromId` node)
  and `toProperty` (an **input** port of the `toId` node)?
- What value types flow through each port, and which conversions are legal
  (`typecasts`)?

**Node types not in the catalog:**

- A `type` beginning with `/` (e.g. `/Pages/Start`) is a reference to a
  **component defined in the same project**, not a library node. Its ports are
  the component's own `Component Inputs`/`Component Outputs` declarations.
- Old projects may reference node types that no longer exist in this codebase
  (e.g. `Rectangle`, `Markdown`, `REST`, `Application Events`, module nodes
  like `module.inlineHtml`). These are genuinely unknown to today's runtime —
  a validator should report them, and an authoring AI must never emit them.

## Top-level fields

| Field | Meaning |
|---|---|
| `catalogFormatVersion` | Semver of this catalog format. Consumers should check the major version. |
| `generatedBy` | Path of the generator script. |
| `schemaDocs` | Path of this document. |
| `packages` | Version of each source package the registries were loaded from. |
| `portTypeNames` | Every distinct port value-type name that occurs in the catalog (see "Port types"). |
| `typecasts` | The runtime's implicit conversion table: a connection from type `from` to any type in `to` is legal. Taken verbatim from the runtime's own table. |
| `nodes` | One entry per registered node type, sorted by `typeName`. |

## Node entry fields

| Field | Meaning |
|---|---|
| `typeName` | The **exact string** used as `node.type` in project files. This is the canonical identity; display names are not valid in files. |
| `displayName` | Human-readable name shown in the editor (e.g. `net.noodl.controls.button` displays as "Button"). |
| `category` | Editor palette category (`Visual`, `Logic`, `Data`, `CustomCode`, …). |
| `isVisual` | `true` if the node renders UI (has a place in the visual tree). Visual nodes may appear as `children` of other visual nodes; logic/data nodes are placed in a component's graph `roots` but never nested under a visual parent. The order of a visual node's `children` array is its layout order. This distinction also drives code export. |
| `isDeprecated` | `true` for nodes kept only for old projects. Valid to read, wrong to author. |
| `inNodePicker` | `true` if the editor's add-node picker offers this type. Several legacy types are registered but superseded and not offered (e.g. the plain `Button`, `CheckBox`, `Options`, `Range`, `TextInput` controls are superseded by their `net.noodl.controls.*` counterparts) — when choosing between same-named alternatives, **prefer the one with `inNodePicker: true`**. A few picker-hidden types are still authored through specialised flows (`Page` as a page component's root, `noodl.cloud.request`/`response` in cloud functions). |
| `availableIn` | Runtime environments that register this type: `browser` (pages/components), `cloud` (cloud-function components, i.e. components under `/#__cloud__/`), or both. |
| `providedBy` | Which registration path provides the type: `noodl-runtime`, `noodl-viewer-react`, `noodl-viewer-cloud`, or `noodl-editor` (editor-only pseudo-nodes). |
| `docs` | Documentation URL, when the definition declares one. |
| `searchTags`, `module`, `shortDesc` | Optional editor search/metadata fields, carried through when present. |
| `singleton` | Only one instance per component graph is meaningful. |
| `allowAsChild` | May be nested as a child of a visual node. |
| `allowChildrenWithCategory` | Categories of nodes this node accepts as children (e.g. `["Visual"]`). Absent → the node takes no children. |
| `allowAsExportRoot` | May be the root of a component's visual tree. |
| `useVariants` | Supports style variants. |
| `visualStates` | Interaction states (`neutral`, `hover`, `pressed`, …) whose parameters can be overridden per state. |
| `inputs` / `outputs` | Statically-declared ports, sorted by name. See "Port entries". |
| `dynamicPorts` | `null` for fully-static nodes; otherwise an object describing how the real port set is determined. See "Dynamic ports". |

## Port entries

| Field | Meaning |
|---|---|
| `name` | Exact string used in `parameters` keys and connection `fromProperty`/`toProperty`. Names may contain spaces and dots (`"scrollToIndex.do"`). |
| `displayName` / `editorName` / `group` | Editor presentation only. |
| `plug` | `input` or `output`. |
| `type` | The value type (see "Port types"). |
| `isSignal` | `true` if this is a pulse/event port rather than a value. Signal inputs are triggered by connections (and never set via `parameters`); signal outputs fire events. |
| `default` | Value used when neither `parameters` nor a connection provides one. For dimension-like types with `defaultUnit`, the stored parameter form is `{ "value": n, "unit": "px" }`. |
| `description` | Plain-text description, when the definition carries a tooltip. |
| `index` | Editor sort hint; no semantic meaning. |
| `allowVisualStates` | Parameter may be overridden per visual state / variant. |
| `hiddenInEditor` | The port exists at runtime but the editor UI does not expose it. Do not author against these. |

**Inputs vs. parameters.** Every non-signal input can be set statically via the
node's `parameters` map *or* driven by a connection. There is no separate
parameter list: `parameters` keys are input port names. Two qualifiers:
`type.allowConnectionsOnly: true` means the port only accepts connections
(never a static parameter); `type.allowEditOnly: true` means the opposite —
parameter only, no connections.

**Precedence:** parameters (or the port default) are applied when the node
instance is created; a connection overwrites that value each time the source
output emits. Until the first connected value arrives, the parameter/default
remains in effect — so giving a connected input a sensible static value is
good practice, not a conflict.

## Port types

`type` is always an object with at least `name`. Common names:
`string`, `number`, `boolean`, `signal`, `color`, `image`, `enum`, `array`,
`object`, `dimension`, `textStyle`, `reference`, `component`, `cloudfile`,
`stringlist`, `proplist`, `dimension`… — the full observed list is in
`portTypeNames`.

Frequent extra keys:

- `enums`: allowed values, as `{ label, value }` pairs (author the `value`,
  not the label) or plain strings. `enumsAreDynamic: true` means the list is
  computed at runtime and not statically known.
- `units` + `defaultUnit`: dimension-style inputs; parameter form
  `{ "value": 100, "unit": "%" }` (plain numbers are interpreted in
  `defaultUnit`).
- `allowConnectionsOnly` / `allowEditOnly`: see above.
- `multiline`, `codeeditor`, and other editor hints may pass through; ignore
  unknown keys.

**Connection legality:** a connection is type-correct if the output's type
name equals the input's, or the pair appears in `typecasts`. Signals only
connect to signals (plus the casts listed for `signal`).

## Dynamic ports

The single most important honesty rule of this catalog: **for many nodes the
static `inputs`/`outputs` lists are incomplete by design**, because the real
port set depends on user code, parameters, or project context. Such nodes have
a non-null `dynamicPorts`:

| Field | Meaning |
|---|---|
| `mechanisms` | How the extra ports come to exist (see below). |
| `description` | What determines the port set, in plain language. Curated for the important nodes, generic otherwise. |
| `declaredPortGroups` | For `declared-port-groups`: the exact conditional groups from the node's metadata — port lists guarded by `condition` expressions over parameter values. These ports *are* statically enumerable given the node's parameters. |
| `numberedInputs` | For `numbered-inputs`: unbounded series named `"<nameBase> <N>"` (`"and 0"`, `"and 1"`, …) counting from 0. |
| `editorAdapter` | For `editor-adapter`: the editor-side class that computes ports (`packages/noodl-editor/src/editor/src/models/NodeTypeAdapters/`). |

Mechanisms:

- `declared-port-groups` — conditionally-visible ports declared in metadata;
  fully enumerable from `declaredPortGroups` + the node's parameters. Each
  group's `condition` is a small expression over parameter values with
  operators `=`, `!=`, `AND`, `OR` and the unary test `<param> NOT SET`
  (e.g. `"useLabel = true OR useLabel NOT SET"`); a port in the group is
  valid when the condition holds for the node's parameters.
- `numbered-inputs` — an indexed input series; any `"<nameBase> <N>"` is valid.
- `component-ports` — the user declares the ports per instance (Component
  Inputs/Outputs `ports` parameter).
- `runtime-discovered` — ports are discovered by running user code or reading
  parameters at runtime (Function/Expression/Script nodes, schema-driven data
  nodes) and pushed to the editor per instance. **These cannot be enumerated
  statically**; a validator must accept unknown port names on such nodes (or
  downgrade them to warnings), and a code generator needs the node's
  parameters to reconstruct them.
- `editor-adapter` — the editor derives ports from project context (routers,
  queries, cloud functions).

For validation the practical rule is: *unknown port on a static node → error;
unknown port on a dynamic node → allowed (optionally warn)*. That rule plus
this catalog reproduced ~5,000 connection-endpoint resolutions across the
repo's real-project test corpus with zero false errors.

## Guarantees and non-guarantees

- Generated from the live registries; the committed artifact is regenerated
  and diffed in CI (`node-catalog` job), so it cannot silently drift.
- Byte-deterministic: the generator runs the extraction twice and refuses to
  publish if the runs differ; nodes and ports are sorted; no timestamps.
- Editor-*display* metadata (panel layouts, node colors, port sort indices)
  is intentionally minimal or absent — this catalog is a semantic contract,
  not a UI description.
- Prose usage documentation and per-node examples are out of scope here and
  arrive with the catalog enrichment task (SUB-005).
